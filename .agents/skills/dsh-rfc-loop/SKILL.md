# DSH RFC 闭环：Lead 只通信，写手与审阅双方落地

本 skill 是一条**完全本地、自包含**的独立流水线，与仓库里其它 RFC 相关 skill 互不调用、不共享流程假设。它只做一件事：把 `docs/rfc/` 下**已经存在**的待办笔记实现成代码，逐篇落到**本地 main**。

## 本 skill 不做

- **不审计、不找候选、不产出新笔记**：待办范围只来自 `docs/rfc/` 下 `Status: proposed` 的既有笔记。查出来 0 条就如实报告「当前没有待办」然后停下，**不要自己找活干**。
- **不碰远端**：不 push、不 fetch 依赖、不开 PR、不用 `gh`、不发版、不写 changelog、不改写 main 历史、不合并别的分支。
- **不替用户做功能取舍**：遇到笔记不可行、会引入用户可观察回归、或超过 3 次裁定，就停下把选择权交回用户。
- **不让 Lead 碰代码**：Lead 不读实现、不改代码、不跑门禁、不做验收（仅按用户明确要求做只读预检与记账）。

## 角色与铁律

| 角色           | 生命周期 | 只做这些                                                       | 绝对不做                                   |
| -------------- | -------- | -------------------------------------------------------------- | ------------------------------------------ |
| **Lead**（你） | 全程     | 跑预检、派活、**原文转述**、卡轮次与停止条件、记账、向用户汇报 | 读实现、改代码、跑门禁、跑验收、做技术裁决 |
| **写手**       | 每篇全新 | 切分支、读该篇笔记、改代码、**跑四条门禁**、`git add -A`、回报 | commit、落地到 main、改 main、改别的 RFC   |
| **审阅**       | 每篇全新 | 评审暂存区、裁定、LGTM 后收口文档 + commit + rebase 落地       | 跑任何 cargo / 构建 / 测试命令、改源码     |

- **唯一门禁执行者 = 写手。** 审阅不跑门禁（省时间与 token），代价是审阅只能读门禁原文。
- **身份链靠结构、不靠检测**：写手不 commit，评审审的是它 add 进去的 index，落地 commit 也由评审从同一个 index 生成——三者同源，所以不需要任何哈希校验。写手把门禁放在最后一步、之后只允许 add 与汇报。
- **同一时刻只允许一个 agent 在写。** 严格串行：上一篇落地前不许派下一篇写手；不许并行跑 cargo（会抢锁且互相污染工作区）。
- Lead 转述分歧时**不带自己的技术判断**：写手反驳审阅时，把双方原话互相转达即可，由审阅裁定。
- 用户明确要求过：Lead **不做验收**。最终汇报必须声明"验收证据来自写手与审阅的报告，Lead 未亲自复现"，不要把二手证据写成自己的结论。

## 模型路由（写死）

| 角色 | provider      | model    | 可选 reasoning_effort  |
| ---- | ------------- | -------- | ---------------------- |
| 写手 | `commandcode` | 用户提供 | `low` / `high` / `max` |
| 审阅 | `commandcode` | 用户提供 | `low` / `high` / `max` |

- `provider` 与 `model` 必须同时给；`model` 用**不带 provider 前缀**的 id（上面两条已用 `list_subagent_models(provider: "commandcode", model: …)` 逐个核实过，横幅里显示的 `commandcode/…` 是全限定名）。
- `reasoning_effort` 默认不指定；审阅觉得不够狠时可提到 `max`，但不要在两个角色上做无声的模型替换。
- 开工前可用 `list_subagent_models(provider: "commandcode")` 复核这两个 id 仍被广告；模型不可用时**停下来问用户**，不要自行替换路由。

派活用 `subagent`（`context` 为全新，**不要用 `subagent_fork`**——它会带上本会话无关上下文）。写手/审阅都是"派一次、按 id 反复续接"：

- 首次：`subagent(prompt, provider, model, description)`
- 续接同一写手（转述审阅裁定 / 要证据）：`send_message(target: <subagent id>, message: ...)`
- 每篇的写手与审阅都**重新派**，不复用上一篇的 id。

## 第 0 步：预检（Lead 亲自跑）

```
bun .agents/skills/dsh-rfc-loop/preflight.ts
```

- 实现是 Bun/TS（与仓库 `scripts/` 一致）；`preflight.ps1` 只是转发壳，逻辑不在那儿。
- 脚本内部用**文件重定向**而不是管道抓 `git` 输出：DSH 受限沙箱禁止子进程用管道捕获输出（Bun/Node 的默认 `stdio: "pipe"` 会 EPERM）。别把它改回 `stdout: "pipe"`。
- 输出 `PREFLIGHT: OK`（退出码 0）才继续；`PREFLIGHT: STOP`（退出码 2）就**原样把输出交给用户并停下**，不要自行修复、不要 stash、不要动分支。
- 把脚本给的 `BASE_SHA`、`TODO[]`、`SESSION_DIRS` 抄进账本。
- 预检的前提由用户保证：**流程期间 main 不会有任何其它变更**。脚本的这条假设不成立时（main 被别的东西动过），审阅落地那步的 fast-forward 判定会兜住。
- 预检要求工作区干净，所以 `.agents/skills/dsh-rfc-loop/` 与 `.gitignore` 里的 `.dsh-rfc-loop-temp/` 规则**必须先提交到 main**（setup 提交）。没提交时预检必然 STOP——那是正确行为，不是脚本坏了。

## 第 1 步：建账本

账本路径 `.dsh-rfc-loop-temp/ledger.md`——仓库根下的临时目录，已在 `.gitignore` 里。被 git 忽略，所以**不进任何提交、也不会让 `git status --porcelain` 变脏**（这正是预检「工作区干净」能通过的前提；预检脚本会核对这条忽略规则，规则失效就直接 STOP）。用 write 工具追加，格式见文末「账本」。

- 目录不存在时由 Lead 首次写账本时一并创建。
- **不要对 `.dsh-rfc-loop-temp/` 跑 `git clean -xdf`**（`-x` 会连它一起删）。账本丢了只损失过程记录，不影响代码、分支与 main。

不建 team 任务板：本流程是严格串行的单链，任务板不带来增量信息，只增加一层要同步的状态。

## 第 2 步：派写手

用 [`prompts.md`](prompts.md) 的「写手提示词模板」，替换占位符：`{{RFC_PATH}}`、`{{BRANCH}}`、`{{BASE_SHA}}`。

- 分支命名：`rfc/<笔记文件名去掉扩展名>`，例 `rfc/10-disclose-download-mirror`。
- **写手不 commit。** 它的交付物是**暂存区**：`git add -A` 之后停止。commit 由审阅在 LGTM 之后执行。
  由此得到一个免费的结构性保证：写手从不 commit，所以**分支的 HEAD 恒等于 `{{BASE_SHA}}`**，`git diff --cached` 永远是「相对 base 的完整变更集」，不存在"审到旧代码"的可能，也不需要每轮重新告诉审阅 base 是谁。
- **门禁是写手的最后一步**：跑完只允许再做两件事——`git add -A`、写报告。**不许再改任何文件**；要改就必须重跑门禁。这是靠**顺序**而不是靠事后检测来保证"过门禁的代码 == 交付的代码"。
- 首次派活必须拿到**齐全**的回报字段（缺任何一项就打回去要，不要替它猜）：
  `RFC 路径 / 分支 / git diff --cached --stat 路径清单 / 四条门禁原文 / 与笔记的偏差 / 不确定项与未实测项 / 是否发现用户可观察回归 / 一句话结论`。
- 写手报「该 RFC 不可行」或「会造成用户可观察回归」→ **立即停**，交用户裁决；**不占 review 轮次、不落地**。
- 写手连续 **2** 次交不出"通过门禁的暂存区"（门禁没过 / 没 add）→ **立即停**，交用户裁决；这两种都不占 review 轮次。

## 第 3 步：派审阅

每篇一个全新审阅子代理，输入：写手回报原文（含门禁原文）、`{{RFC_PATH}}`、`{{BRANCH}}`、`{{BASE_SHA}}`，外加 [`prompts.md`](prompts.md) 的「审阅提示词模板」。

审阅的**评审范围**（写进提示词；注意这里没有阻塞检查）：

- **主输入**：`git diff --cached`（全量，不许抽样）。
- **附带**：`git diff` 与 `git status` —— 只看一眼有没有未暂存/未跟踪内容。**干净就略过、不写进报告**；有内容才在报告里记一笔，且不因此阻塞（除非它直接影响评审结论）。审阅读源码走的是磁盘内容，一旦与 diff 对不上它自己就会发现——这是自带信号的失配，不需要专门检测。

审阅的硬边界（提示词里也要写死）：

- **禁止执行任何 cargo / 构建 / 测试命令**，也禁止 commit、checkout、stash、rebase——唯一例外是裁定 LGTM 之后的收口与落地阶段。
- 允许的 git 命令只有只读的：`diff`、`status`、`log`、`show`、`rev-parse`、`blame`、`merge-base`。
- 判断不了的事实写成 `<需要写手提供证据：…>`，由 Lead 转述给写手，**不要自己跑**。

回报字段：`裁定（LGTM / 变更要求）` + 每条 `文件:行 + 证据 + 要求 + 严重级（阻塞/建议）` + （LGTM 时）落地执行报告。

- **只有「阻塞」项必须解决。** 「建议」项默认**不转**给写手（避免范围扩散），只记进账本，最终汇报时列出。

## 第 4 步：转述与轮次

- **轮次 = 审阅的每一次裁定**（LGTM 或非 LGTM 都算一次交流）。
- 非 LGTM：把审阅裁定**原文**用 `send_message` 转给**同一个写手**（保持其上下文），附上剩余轮次和"可以反驳"的规则。
- 写手可以**反驳**：反驳必须带证据（`文件:行` / 门禁原文 / 规范原文）。Lead 只转述，不替任何一方站台。写手反驳后审阅必须重新裁定 → 进入下一轮。
- 写手返工时必须**重跑门禁 + 重新 `git add -A`**；漏了 `git add` 就是把旧代码重新交给审阅，所以提示词里要写死这一步。
- **第 3 次裁定仍非 LGTM → 停止**：不再给写手任何消息、不落地、**保持现状、不做任何清理**（main 不动、分支保留、暂存区原样留着）。脏 index 本身就是最完整的证据（改动 + 暂存状态都在），加上 agent 的执行记录，足够用户复盘为什么谈崩；下次预检会因为工作区脏而 STOP，而 STOP 的定义本来就是"停下来问用户"，语义自洽。

## 第 5 步：LGTM 之后的收口与落地（审阅自己完成）

审阅按顺序执行，**任一步失败即停并上报，不许自行修复**：

1. **收口文档**：笔记的 `Status: proposed` 改成 `Status: implemented`（**只改这一行**，不写日期、不写 sha）；移动到 `docs/archive/rfc/<同一会话目录>/`。然后 `git add` **只这一个笔记的旧路径和新路径**——写手已把笔记以 `proposed` 状态 add 进 index 了，不重新 add 就会提交一份 `proposed`，而且旧路径与新路径会同时留在 index 里，收口静默失效。**不要用 `git add -A`。**
2. **commit**：此时分支上只有这一个 commit。提交信息按 `AGENTS.md` 五问（改了什么 / 为什么改 / 对本应用的影响 / 对用户的影响 / 破坏性变更），中文 + conventional 前缀，先 `git log -6` 对齐风格，**禁止出现「详见 docs/rfc/...」「见 RFC 笔记」这类把答案推给别处的引用**。
3. **落地**：`git checkout main` → `git rebase rfc/<…>`，走 fast-forward 落到 main。审阅**必须确认 rebase 是 fast-forward**（输出里 main 直接落到分支那条提交、没有 `Applying …` 之类的重放行）并把输出原样贴进报告；出现 conflict、检出 detached HEAD、或没有 fast-forward → **停**，不许自行解决。分支是从未变动的 main 上切出、且只有 1 个 commit，所以 rebase 退化成纯指针移动，tree 按 git 语义不可能变。
4. **保留** `rfc/<…>` 分支，不删除（用户已确认，用于留证据与回滚）。
5. 回报：落地 commit sha、`git log -1` 原文、rebase 输出（证明是 ff）、落地后 `git status --porcelain`（必须为空）、`git log --oneline -2`（证明 main 只多了一个提交）。

## 第 6 步：下一篇

- 只有审阅回报「已落地 + fast-forward 已确认 + `git status` 干净」后，才允许派下一篇写手；新的 `{{BASE_SHA}}` = 新的 `main` HEAD（写手分支必须从它切出，这是"不可能有冲突"的唯一前提）。
- 全部待办落地后，Lead 只做一件事：按账本核对每篇笔记是否都已出现在 `docs/archive/rfc/<会话目录>/` 且为 `Status: implemented`，没完成的列为未完成。**不跑门禁、不做验收、不 push、不发版、不写 changelog。**
- 结束汇报：逐篇的落地 commit、评审轮次与裁定、被驳回/反驳的要点、未解决的"建议"项、未完成项，以及那句"验收证据来自写手与审阅的报告，Lead 未亲自复现"。

## 审阅标准（写手与审阅共享）

1. **身份链**（结构性保证，不靠检测）：写手从不 commit，评审审的就是它 `git add` 进去的那个 index，落地 commit 也由评审从同一个 index 生成——所以"过门禁的 == 被审的 == 落地的"三者同源，无需任何哈希校验。门禁靠**顺序**保证是最后一步。
2. **范围**：diff == 笔记「提案」段；「明确不在本次范围」是硬边界；无格式重排、无关重命名、顺手重构。
3. **`AGENTS.md`**（自动注入，未注入就先读）：受保护接缝未被碰；`unsafe` 注释说明真实不变量（不是复述"句柄来自成功的 OS API"）；生产路径无新增 `unwrap`/`expect`；新增说明性用户文案是中文。
4. **笔记的「验收标准」逐条对账**，不许跳条、不许以"等价"含混带过。
5. **测试**：行为变更处有覆盖；删了测试必须点名哪条更强的用例接管了那条性质。
6. **笔记是规范**：实施中发现行号/计数/事实与代码不符，改笔记（写手的职责），而不是让代码偏离规范。
7. **提交信息**：分支上只有一条 commit，五问必须齐全、自足、不指向文档。

## 停止条件（命中任一：全线停，不做任何补救）

- 预检非 OK；`main` 在流程中被改动；写手报不可行/用户可观察回归；写手连续 2 次交不出通过门禁的暂存区；审阅第 3 次裁定仍非 LGTM；落地时 rebase 不是 fast-forward；流程里冒出「必须 push / 开 PR / 发版 / 改写 main 历史 / 改依赖才能构建」这类需求（本流程是离线的本地闭环，本不该出现）。
- 停下时的统一姿态：**main 不动、分支保留、暂存区原样留着、不清理任何东西**，把账本与原始证据交给用户，等裁决。

## 账本

`.dsh-rfc-loop-temp/ledger.md`（git 已忽略，不进提交）：

```
## <RFC 文件名>
- base: <sha>   branch: rfc/<...>
- 轮次: 1) 非LGTM <审阅要点> ；2) 写手反驳 <要点> → 审阅非LGTM ；3) LGTM
- 门禁原文: <writer 回报里的原文，或注明"见第 N 轮消息">
- "建议"项(未处理): <…>
- landed: <commit sha>   (ff 落地)
- 状态: landed / 停止-等裁决（现状保留，脏 index 是证据）/ 未开始
```
