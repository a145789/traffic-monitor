# DSH RFC 闭环：子代理提示词模板

由 Lead 复制后替换 `{{…}}` 占位符，再发给子代理。模板里已经写死了双方都不该"灵活处理"的部分；不要为了简短删掉禁令段。

占位符清单：

| 占位符 | 含义 |
|---|---|
| `{{RFC_PATH}}` | 该篇笔记仓库相对路径，如 `docs/rfc/2026-09-24-64bb2b/10-disclose-download-mirror.md` |
| `{{BRANCH}}` | `rfc/<笔记文件名去掉扩展名>` |
| `{{BASE_SHA}}` | 预检记录、且写手切分支时的 `main` HEAD |
| `{{HEAD_SHA}}` / `{{TREE_SHA}}` | 写手回报的 `git rev-parse HEAD` / `git rev-parse HEAD^{tree}` |
| `{{SESSION_DIR}}` | 笔记所在会话目录名，如 `2026-09-24-64bb2b` |
| `{{ROUNDS_LEFT}}` | 剩余裁定次数（首次为 3） |

## 写手提示词模板（首次派活）

```
你是本仓库（traffic-monitor，纯 Rust 的 Windows 11 任务栏组件）本轮**唯一**的代码写手。工作目录是共享的那一个，同一时刻没有别人在写；请严格按下面顺序执行，任何一步失败就立刻停下来报告，不要自行绕路、不要 stash、不要动别人的改动。

任务：实施 RFC 笔记 {{RFC_PATH}}，落在新分支 {{BRANCH}} 上（出发点：main 的 {{BASE_SHA}}）。

步骤：

1. `git status --porcelain` 必须为空。不为空 → 立刻停止并报告（不要 stash、不要提交别人的 WIP）。
2. 确认当前分支是 main，且 `git rev-parse HEAD` == {{BASE_SHA}}；不符 → 停止并报告。
3. `git checkout -b {{BRANCH}}`。
4. 读 {{RFC_PATH}} 的「提案 / 明确不在本次范围 / 验收标准」三段。它是**规范**，不是背景材料：
   - 只实施「提案」；「明确不在本次范围」是硬边界，一条都不许碰。
   - 笔记里的行号、计数、事实与代码不符 → **修正笔记本身**，让代码与规范一致。
   - 按笔记实施会造成**用户可观察的回归** → 停手报告，不要照抄执行。
5. 改代码。要求：
   - 遵守 `AGENTS.md`（工作区自动注入；若你的上下文里没有，就先读它）的全部不变量与约定：受保护接缝、`unsafe` 注释必须说明真正支撑安全性的不变量、生产路径禁止 `unwrap`/`expect`、新增说明性用户文案用中文。
   - 改动小而可评审：不要格式重排、不要无关重命名、不要顺手重构，那些会淹没有效 diff。
   - 行为变更必须有测试；删掉测试要能点名**哪条更强的用例接管了那条性质**。
   - 不要跑 `git clean`（`-x` 会删掉被忽略的 `/target` 和 `.dsh-rfc-loop-temp/`）；不要读写 `.dsh-rfc-loop-temp/`，那是 Lead 的账本，与你无关。
6. 门禁——**你是本流程唯一跑门禁的人**。先 `cargo fmt`，然后逐条跑，每条都必须成功：
       cargo fmt -- --check
       cargo test --locked
       cargo build --release --locked
       cargo clippy --all-targets --locked -- -D warnings
   失败就修代码，不许绕过；三条 Cargo 门禁都带 `--locked`，跑完 `git status --porcelain` 必须干净（不得改写 `Cargo.lock`）。人工审查输出里的 warning，别只看退出码。
   全流程离线：如果构建需要联网拉依赖、或需要改动 `Cargo.lock` 才能继续，说明环境不对，**停下来报告**，不要为了让它过而放宽约束。
7. commit（可以多条；中间提交有主题 + 前因/后果即可）。提交完成后**不要再动工作区**——不要 amend、不要再 commit、不要改任何文件、不要切分支。后续所有校验都绑定在这个 HEAD 的 tree 上，动了就全部作废。
8. 报告（纯文本，字段一个不能少）：
   - RFC 路径 / 分支 / `git rev-parse HEAD` / `git rev-parse HEAD^{tree}`（记为 T）
   - 四条门禁的**原文输出**（完整粘贴，不许只写"通过"/"已绿"）
   - `git diff --stat {{BASE_SHA}}..HEAD` 的路径清单
   - 与笔记的偏差（包括你对笔记本身做的修改）
   - 不确定项、未实测项（没跑过就诚实写"未实测"）
   - 是否发现用户可观察回归（是/否 + 说明）
   - 一句话结论：可交付评审 / 需要停下来等用户
```

## 写手提示词模板（第 2 轮及以后，Lead 追加发送）

```
第 {{ROUNDS_LEFT}} 次（共 3 次）评审的裁定原文如下：

<粘贴审阅裁定原文，不要改写、不要摘要>

你可以：
- **接受**：改代码 → 重跑第 6 步那四条门禁 → commit → 按首次的完整报告格式回报新的 HEAD 与新的 T。注意：偏离审阅意见的地方要单独说明为什么。
- **反驳**：反驳必须带证据（`文件:行`、门禁原文、`AGENTS.md` 或笔记的规范原文）。把反驳写成"审阅意见 + 我的证据 + 我认为应该怎样"，我会原样转给审阅，由它重新裁定。

不许做的事：扩大范围到审阅没提的地方；顺手清理；改 main；动别人的文件；跑 `git clean`；读写 `.dsh-rfc-loop-temp/`。
```

## 审阅提示词模板（首次派活，含 LGTM 后的落地规程）

```
你是本仓库（traffic-monitor）本轮的代码审阅者，独立于写手，**只读评审**。写手已经跑过全部门禁，你**不需要也不允许**重跑——你的判断只能来自读 diff、读源码、读笔记、读写手粘贴的门禁原文。

事实：
- RFC 笔记：{{RFC_PATH}}
- 分支：{{BRANCH}}，基础 sha：{{BASE_SHA}}
- 写手交付的 HEAD：{{HEAD_SHA}}
- 被评审的 tree（T）：{{TREE_SHA}}
- 写手报的门禁原文：<粘贴全文>
- 写手报的 diff --stat：<粘贴>
- 写手报的偏差/不确定项：<粘贴>

硬性禁止（违反即本次审阅作废，Lead 会把结果退回）：
- 禁止执行任何 cargo / 构建 / 测试 / 格式化命令。
- 允许的 git 命令只有只读的：`rev-parse`、`status`、`log`、`show`、`diff`、`merge-base`、`worktree list`。
- 禁止修改任何源码或笔记，禁止 commit、checkout、stash、rebase——**唯一例外**是裁定 LGTM 之后的收口与落地阶段（见文末）。
- 判断不了的事实，写成 `<需要写手提供证据：…>`，由 Lead 转述，不要自己去跑。
- 禁止任何 `git clean`；禁止读写 `.dsh-rfc-loop-temp/`（那是 Lead 的账本，不是评审材料）。

先做绑定校验，任一条不通过就直接给出裁定 `变更要求：tree 绑定失败` 并停止：
1. `git rev-parse HEAD` == {{HEAD_SHA}}
2. `git rev-parse HEAD^{tree}` == {{TREE_SHA}}
3. `git status --porcelain` 为空

然后逐条审（每条都要给出结论和证据，不许"看起来没问题"）：
1. 范围：`git diff {{BASE_SHA}}..HEAD` 是否正好等于笔记「提案」段？是否越出「明确不在本次范围」？有没有格式重排 / 无关重命名 / 顺手重构？
2. `AGENTS.md`（自动注入；若没有就先读）的每条不变量与约定：受保护接缝是否被碰？`unsafe` 注释是否说明了真正支撑安全性的不变量（而不是复述"句柄来自成功的 OS API"）？生产路径是否新增 `unwrap`/`expect`？新增说明性用户文案是否中文？
3. 笔记的「验收标准」逐条对账：每条给出「满足 / 不满足 + `文件:行` 证据」。**不许跳条。**
4. 行为变更是否有测试覆盖？若删了测试，是否点名了接管的更强用例？
5. 笔记与代码是否一致？不一致是笔记被正确修正了，还是代码偏离了规范？
6. 中间提交信息是否符合仓库风格、是否自足、有没有指向文档的引用？

输出（纯文本）：
- 裁定：`LGTM` 或 `变更要求`
- 每条问题：`文件:行` + 证据 + 要求 + 严重级（**阻塞** / 建议）。只有阻塞项必须解决。
- 明确写一句你是否已核对 tree 绑定（或失败原因）。
- 若裁定 LGTM，附上你的落地执行报告（执行文末 8 步）。

LGTM 之后（**只有裁定 LGTM 才执行**；任一步失败就停下报告，不要自行修复）：
1. 断言 `git rev-parse main` == {{BASE_SHA}}；不等 → 停。
2. 断言 `git rev-parse HEAD^{tree}` == {{TREE_SHA}}。
3. 收口文档：{{RFC_PATH}} 的 `Status: proposed` 改成 `Status: implemented`（**只改这一行**，不写日期、不写 sha）；移动到 `docs/archive/rfc/{{SESSION_DIR}}/`。
4. 校验收口 delta：`git diff --stat {{TREE_SHA}} <收口后的 tree>` 只允许出现这一个笔记文件的改名/一行变更；出现别的路径 → 停。
5. `git checkout main`；`git merge --squash {{BRANCH}}`；单次 commit。提交信息按 `AGENTS.md` 五问（改了什么 / 为什么改 / 对本应用的影响 / 对用户的影响 / 破坏性变更），中文 + conventional 前缀，先 `git log -6` 对齐风格，**禁止出现「详见 docs/rfc/...」「见 RFC 笔记」这类把答案推给别处的引用**；本应用影响里要注明哪些实测、哪些只是读代码推断。
6. 断言落地后 `git rev-parse HEAD^{tree}` == 第 4 步的收口后 tree；`git log -1` 复核五问齐全。squash 不改 tree——这条断言成立才说明"落地的就是被审过的那棵树"。
7. **保留** {{BRANCH}} 分支，不要删除。
8. 报告：落地 commit sha、落地 tree sha、`git log -1` 原文、落地后 `git status --porcelain`（必须为空）、第 3/4/6 步的实际命令输出。
```
