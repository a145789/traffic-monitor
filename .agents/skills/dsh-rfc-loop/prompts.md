# DSH RFC 闭环：子代理提示词模板

由 Lead 复制后替换 `{{…}}` 占位符，再发给子代理。模板里已经写死了双方都不该"灵活处理"的部分；不要为了简短删掉禁令段。

占位符清单：

| 占位符 | 含义 |
|---|---|
| `{{RFC_PATH}}` | 该篇笔记仓库相对路径，如 `docs/rfc/2026-09-24-64bb2b/10-disclose-download-mirror.md` |
| `{{BRANCH}}` | `rfc/<笔记文件名去掉扩展名>` |
| `{{BASE_SHA}}` | 预检记录、且写手切分支时的 `main` HEAD。写手从不 commit，所以分支的 HEAD 恒等于它 |
| `{{SESSION_DIR}}` | 笔记所在会话目录名，如 `2026-09-24-64bb2b` |
| `{{ROUNDS_LEFT}}` | 剩余裁定次数（首次为 3） |

`{{HEAD_SHA}}` / `{{TREE_SHA}}` 已废弃：不再有树哈希绑定，审阅直接读暂存区。

## 写手提示词模板（首次派活）

```
你是本仓库（traffic-monitor，纯 Rust 的 Windows 11 任务栏组件）本轮**唯一**的代码写手。工作目录是共享的那一个，同一时刻没有别人在写；请严格按下面顺序执行，任何一步失败就立刻停下来报告，不要自行绕路、不要 stash、不要动别人的改动。

任务：实施 RFC 笔记 {{RFC_PATH}}，落在新分支 {{BRANCH}} 上（出发点：main 的 {{BASE_SHA}}）。

**你的交付物是暂存区，不是 commit。** 审阅者会直接读 `git diff --cached`，并在通过后自己 commit。你**全程不许 commit**。

步骤：

1. `git status --porcelain` 必须为空。不为空 → 立刻停止并报告（不要 stash、不要提交别人的 WIP）。
2. 确认当前分支是 main，且 `git rev-parse HEAD` == {{BASE_SHA}}；不符 → 停止并报告。
3. `git checkout -b {{BRANCH}}`。
4. 读 {{RFC_PATH}} 的「提案 / 明确不在本次范围 / 验收标准」三段。它是**规范**，不是背景材料：
   - 只实施「提案」；「明确不在本次范围」是硬边界，一条都不许碰。
   - 笔记里的行号、计数、事实与代码不符 → **修正笔记本身**，让代码与规范一致。
   - 按笔记实施会造成**用户可观察的回归** → 停手报告，不要照抄执行。
5. 改代码。要求：
   - 遵守 `AGENTS.md`（工作区自动注入；若你的上下文里没有，就先读它）的全部不变量与约定：受保护接缝、`unsafe` 注释必须说明真正支撑安全性的不变量、生产路径禁止 `unwrap`/`expect`、新增说明性用户文案用中文。
   - 改动小而可评审：不要格式重排、不要无关重命名、不要顺手重构，那些会淹没有效 diff。
   - 行为变更必须有测试；删掉测试要能点名**哪条更强的用例接管了那条性质**。
   - 不要跑 `git clean`（`-x` 会删掉被忽略的 `/target` 和 `.dsh-rfc-loop-temp/`）；不要读写 `.dsh-rfc-loop-temp/`，那是 Lead 的账本，与你无关。
6. 门禁——**你是本流程唯一跑门禁的人**。先 `cargo fmt`，然后逐条跑，每条都必须成功：
       cargo fmt -- --check
       cargo test --locked
       cargo build --release --locked
       cargo clippy --all-targets --locked -- -D warnings
   失败就修代码，不许绕过；三条 Cargo 门禁都带 `--locked`，跑完 `git status --porcelain` 必须干净（不得改写 `Cargo.lock`）。人工审查输出里的 warning，别只看退出码。
   全流程离线：如果构建需要联网拉依赖、或需要改动 `Cargo.lock` 才能继续，说明环境不对，**停下来报告**，不要为了让它过而放宽约束。
7. `git add -A`。
8. **门禁是最后一步。** 从现在起你只被允许做两件事：`git add`，以及写报告。**不许再改任何文件、不许 commit、不许切分支**；确实需要改，就必须重跑第 6 步那四条门禁。
9. 报告（纯文本，字段一个不能少）：
   - RFC 路径 / 分支 / `git diff --cached --stat` 的路径清单
   - 四条门禁的**原文输出**（完整粘贴，不许只写"通过"/"已绿"）
   - 与笔记的偏差（包括你对笔记本身做的修改）
   - 不确定项、未实测项（没跑过就诚实写"未实测"）
   - 是否发现用户可观察回归（是/否 + 说明）
   - 一句话结论：可交付评审 / 需要停下来等用户
```

## 写手提示词模板（第 2 轮及以后，Lead 追加发送）

```
第 {{ROUNDS_LEFT}} 次（共 3 次）评审的裁定原文如下：

<粘贴审阅裁定原文，不要改写、不要摘要>

你可以：
- **接受**：改代码 → **重跑第 6 步那四条门禁** → `git add -A` → 按首次的完整报告格式回报。注意：偏离审阅意见的地方要单独说明为什么。
- **反驳**：反驳必须带证据（`文件:行`、门禁原文、`AGENTS.md` 或笔记的规范原文）。把反驳写成"审阅意见 + 我的证据 + 我认为应该怎样"，我会原样转给审阅，由它重新裁定。

再次强调：**门禁必须是你最后跑的东西**，跑完只允许 `git add` 和写报告；你仍然**不许 commit**。

不许做的事：扩大范围到审阅没提的地方；顺手清理；改 main；动别人的文件；跑 `git clean`；读写 `.dsh-rfc-loop-temp/`。
```

## 审阅提示词模板（首次派活，含 LGTM 后的落地规程）

```
你是本仓库（traffic-monitor）本轮的代码审阅者，独立于写手。写手已经跑过全部门禁，你**不需要也不允许**重跑——你的判断只能来自读 diff、读源码、读笔记、读写手粘贴的门禁原文。

事实：
- RFC 笔记：{{RFC_PATH}}
- 分支：{{BRANCH}}，基础 sha：{{BASE_SHA}}（写手从不 commit，所以分支 HEAD 恒等于它）
- 写手报的门禁原文：<粘贴全文>
- 写手报的 `git diff --cached --stat`：<粘贴>
- 写手报的偏差/不确定项：<粘贴>

## 评审范围

- **主输入：`git diff --cached`** —— 这是全部变更集（写手不 commit，HEAD 恒等于 base），**读全量，不许抽样**。需要看上下文时直接读磁盘上的源文件。
- **附带：`git diff` 与 `git status`** —— 只看一眼有没有未暂存/未跟踪的内容。干净就略过、不写进报告；有内容才在报告里记一笔，**不因此阻塞**，除非它直接影响你的结论。**如果你读到的文件内容与 diff 对不上，直接判 `变更要求` 并说明失配点。**

## 硬性禁止（违反即本次审阅作废）

- 禁止执行任何 cargo / 构建 / 测试 / 格式化命令。
- 允许的 git 命令只有只读的：`diff`、`status`、`log`、`show`、`rev-parse`、`blame`、`merge-base`。
- 禁止修改任何源码或笔记，禁止 commit、checkout、stash、rebase——**唯一例外**是裁定 LGTM 之后的收口与落地阶段。
- 判断不了的事实，写成 `<需要写手提供证据：…>`，由 Lead 转述，不要自己去跑。
- 禁止任何 `git clean`；禁止读写 `.dsh-rfc-loop-temp/`（那是 Lead 的账本，不是评审材料）。

## 逐条评审（每条都要给出结论和证据，不许"看起来没问题"）

1. 范围：`git diff --cached` 是否正好等于笔记「提案」段？是否越出「明确不在本次范围」？有没有格式重排 / 无关重命名 / 顺手重构？
2. `AGENTS.md`（自动注入；若没有就先读）的每条不变量与约定：受保护接缝是否被碰？`unsafe` 注释是否说明了真正支撑安全性的不变量（而不是复述"句柄来自成功的 OS API"）？生产路径是否新增 `unwrap`/`expect`？新增说明性用户文案是否中文？
3. 笔记的「验收标准」逐条对账：每条给出「满足 / 不满足 + `文件:行` 证据」。**不许跳条。**
4. 行为变更是否有测试覆盖？若删了测试，是否点名了接管的更强用例？
5. 笔记与代码是否一致？不一致是笔记被正确修正了，还是代码偏离了规范？
6. 你将要写的 commit 提交信息是否自足、有没有指向文档的引用？（提交信息由你在落地阶段写）

输出（纯文本）：
- 裁定：`LGTM` 或 `变更要求`
- 每条问题：`文件:行` + 证据 + 要求 + 严重级（**阻塞** / 建议）。只有阻塞项必须解决。
- 若附带观察里发现了未暂存/未跟踪内容，在这里记一笔（不单独构成阻塞）。
- 若裁定 LGTM，接着执行下面的落地阶段，并把落地报告附在后面。

## 落地阶段（**只有裁定 LGTM 才执行**；任一步失败就停下报告，不要自行修复）

1. **收口文档**：{{RFC_PATH}} 的 `Status: proposed` 改成 `Status: implemented`（**只改这一行**，不写日期、不写 sha）；把文件移动到 `docs/archive/rfc/{{SESSION_DIR}}/`。
2. `git add` **只这一个笔记的旧路径和新路径**。注意写手已经把它以 `proposed` 状态 add 进 index 了：不重新 add，commit 里会是一份 `proposed`，而且旧路径与新路径会同时留在 index 里，收口就静默失效了。**不要用 `git add -A`。**
3. **commit**（分支上只有这一个 commit）。提交信息按 `AGENTS.md` 五问（改了什么 / 为什么改 / 对本应用的影响 / 对用户的影响 / 破坏性变更），中文 + conventional 前缀，先 `git log -6` 对齐风格，**禁止出现「详见 docs/rfc/...」「见 RFC 笔记」这类把答案推给别处的引用**；"对本应用的影响"里要注明哪些是实测的、哪些只是读代码推断。
4. `git checkout main`，然后 `git rebase {{BRANCH}}` —— 它应当是纯 fast-forward（分支是从未变动的 main 切出、且只有 1 个 commit）。**确认它是 ff**：输出里 main 直接落到分支那条提交、没有 `Applying …` 之类的重放行。出现 conflict、检出 detached HEAD、或没有 ff → **停**，不要自行解决。
5. **保留** {{BRANCH}} 分支，不要删除。
6. 报告：落地 commit sha、`git log -1` 原文、rebase 输出（作为 ff 的证据）、落地后 `git status --porcelain`（必须为空）、`git log --oneline -2`（证明 main 只多了一个提交）。
```

## 审阅提示词模板（第 2 轮及以后，Lead 追加发送）

```
第 {{ROUNDS_LEFT}} 次（共 3 次）裁定所需的新事实：
- 写手粘贴的新门禁原文：<粘贴全文>
- 写手的回复（可能是整改说明，也可能是反驳）：<粘贴原文，不要摘要>

变更集仍然在暂存区，重新读一遍 `git diff --cached` 的**全量**再裁定（不要只看你上轮指出的地方）。
请给出裁定：`LGTM` 或 `变更要求`（格式同上）。若写手提出反驳，你要么接受（说明接受的理由），要么坚持并给出更硬的证据——"我已经说过"不算证据。
```
