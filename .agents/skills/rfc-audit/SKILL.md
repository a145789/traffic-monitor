# RFC 审计：从「找找能简化什么」到证据支撑的中文 RFC 笔记

本 skill 只做一件事：**产出带证据的候选，写成笔记**。不实施、不提交、不开 PR。实施与 PR 由 `rfc-ship` 负责。

## 姿态：只读 code，不读文档

用户对本仓库的明确要求是**尽量少读、最好不读已有文档**，依据当前 code 做分析。这不只是省 token，也是准确性要求——历史笔记可能过时，而「是否已有人提过这件事」的真正判据是**代码**。

- **默认不读 `docs/` 下任何内容**，含 `docs/archive/`（历史 RFC、审计、调研与**全部已实施笔记**都在那里）。实测 `docs/archive/` 23 篇 173 KB ≈ 5 万 token，约等于把整个 `src/` 再读一遍，且明确可能过时。
- **`AGENTS.md` 通常已由 harness 自动注入上下文**（作为 workspace instructions）。先确认它在不在上下文里：在，就**不要再 read 一遍**；不在，才读一次，并且只取第 1–9 条受保护接缝。
- **唯一允许进上下文的文档是待办笔记本身**（按下面的分级读法），且只读需要的小节。
- 不要为「更全面了解项目」而通读任何目录；不要给 `docs/rfc/` 维护索引文件（状态行会被 `rfc-ship` 改动，索引必然漂移，反而制造第二个真值来源）。

## 第 0 步：查重（近乎零成本）

```
grep -rn "^Status: *proposed" docs/rfc/
```

**只认 `docs/rfc/<会话目录>/NN-*.md` 的命中**；`docs/rfc/README.md` 里的是格式示例，不是待办（该文件的示例已缩进，正常不会再命中）。

1. **0 条待办** ⇒ 没有重叠风险，直接开工。**不要**为了「了解上下文」去翻 archive。
2. **有 N 条** ⇒ 每条只读**标题 + `## 问题` 段**（`read` 带 `limit` 取前 ~30 行），目的是拿到它点了哪些符号。一次审计的待办通常是个位数，这一步代价可忽略。
3. **只在候选与之可能撞车时才深读**：用**符号级 grep 交叉验证**——本 skill 本来就要求对候选符号做精确 grep，那次 grep 就足以判定重叠。
   - 符号在 `src/` 里**存在** ⇒ 没人删过它，可能与该笔记提案重叠，**此时才**读那篇的 `## 提案` 与 `## 明确不在本次范围`。
   - 符号已**不存在** ⇒ 早已实施，直接跳过，连笔记都不用读。

## 环境事实（本项目特有，写错会白费动作）

- **`rg` 不在 PATH 上。** 用 **grep 工具**（搜索**不需要**先 read 文件；read-first 只约束 `edit`/`write`）或 PowerShell 的 `Select-String`。**给子代理下指令时也必须说明这一点**，否则它们会照抄 `rg` 而全部失败。
- 这是纯 Rust + Win32 项目，源文件在 `src/`，共 17 个。生产语料还包括 `build.rs`、`scripts/*.ts`、`.github/`、`installer.iss`、`Cargo.toml`。
- 测试全部内联在 `src/` 的 `#[cfg(test)]` 模块里，**没有 `tests/` 目录**，也没有 `examples/`。
- 用户可见字符串一律中文；笔记正文用中文。
- **没有自动死代码工具**：无 knip 类比物（那是 JS 生态的），也没有 `cargo-machete` / `cargo-udeps`；`tools/` 是空目录。证据只能手工取，例如 `cargo tree -i <crate>`、`grep -rn "<crate>::" src`、`grep -rn "^use " src`。
- 笔记是**新建 Markdown**：仓库 `core.autocrlf=true` 且无 `.gitattributes`，实测 LF 与 CRLF 会归一化成同一个 blob、`git status` 两种都干净，所以 **LF 不会造成 git 纠缠**；写 CRLF 只是为了与工作区其余文件（都是 CRLF）保持一致。**不要为这条做全仓 EOL 转换。**

## 分类消费者（本 skill 的核心动作）

对每个候选符号，先分类，再判断：

- **生产语料**：`src/*`、`build.rs`、`scripts/*.ts`、loader/CI 配置、`installer.iss`。
- **非生产语料**：`#[cfg(test)]` 测试、README、`docs/`、注释、生成的期望输出。
- **模糊语料**：可能是产品冒烟路径的脚本或示例——**必须读用法再归类**。

先按精确符号 grep（`符号名`、`.name(` 与 `name(`、`事件名`、`配置键`、`线上字符串`），**再读调用点**。任何工具都不能替代理解。

## 什么算强候选

- 公开方法 / 事件 / 配置项 / 辅助函数 / 常量 / 持久化事件 / 测试产物**没有生产消费者**。
- 测试或文档是唯一消费者，且它们钉死的行为不承重。
- **同一事实有两份表示**——尤其是一个 `AtomicBool` / 标志镜像另一个计数器、集合，或纯函数内部的判断。本仓库删过两个同类（一个「有可用网卡」标志与 `!map.is_empty()` 逐字等价；一个「首采样已初始化」标志与纯函数里「历史里有该 LUID」表达同一语义），两者均已落地删除，**同类问题仍可能出现**。
- 一个纯函数已经承担了某职责（且有测试钉死），而调用方又平行实现了一遍。
- 接缝上每个实现都必须支持、但没有消费者使用的方法。
- 只为测试/演示存在的包或模块，带来发布或依赖开销。
- **推测性产品通用性**：为没有产品归属者的场景预留的开关、分支、状态位。
- 不可达分支 / 永不触发的兜底 / 没有生产者的错误路径。
- **手写代码重复实现了标准库或已依赖的 crate 已提供的能力**，且替换能删掉实现**加**其专用测试。评估时要说清：包覆盖了哪部分、哪些残余语义它不管（残余语义计入反对票）。
- **弱测试**值得单独成条：注释声称守护某性质，但断言**无法区分正确实现与注释所指的错误实现**。判定方法：把被测代码换成注释所指的错误实现，断言是否仍通过？仍通过即不具区分力。本仓库用这个方法删掉过三条（同一个 `Instant` 自比守护 `saturating_duration_since`、对任意串恒真的哈希大小写重言式、对空结果恒真的协议扫描断言），现已全部删除——同类仍可能出现。**必须同时证明删除不减保护**——即该性质另有更强的用例覆盖。

## 什么不算（薄候选）

- 「这里看着复杂」但拿不出调用点证据。
- 错别字、单次工具输出、只删一行的等价改写。
- 删除 `AGENTS.md` 保护的接缝本身，或用户从未授权的架构级删除。
- 有真实生产调用方的改动——**那是产品决策，不是清理**。
- 旧笔记里提过、但当前 code 里已经不存在的问题（已实施的东西）。

## 拒绝或降级

- 有生产调用方 → 降级为产品决策，写进「被否决」而不是提案。
- 被 `AGENTS.md` 条款或既有提案明确保护，而新证据**打不过**那条理由。
- 删除会引发无关改动，却没有真正缩小公开 API 或必需行为。
- 想法正确但太小 → 加一条行内 `TODO(tag)`，不要立笔记（见文末）。

## 待办笔记若写着「已实施」

待办目录里的笔记点名的符号在 `src/` 里零命中 ⇒ 它多半早已实施，只是状态字没更新（本仓库真实发生过：5 篇全已实施却仍写 `Status: proposed`）。查法：

```
git log --oneline -15                     # 看有无对应 refactor/fix 提交
git grep -n "<笔记里点名的符号>" -- src     # 零命中 ⇒ 多半已实施
```

零命中就跳过它，顺手在交付说明里指出状态字过期。**不要为了核实而打开 archive 里的笔记**——那正是本 skill 要避免的上下文消耗。

## 笔记格式（逐字遵守）

位置：`docs/rfc/<yyyy-mm-dd>-<会话id前6位>/NN-<topic>.md`

- **会话 ID** 取 `$env:DSH_SESSION_ID`（形如 `session-05939a7b-3169-…`），用 `session-` 之后的 6 位，例：`docs/rfc/2026-09-10-05939a/`。取不到时用简短的 kebab-case 主题词兜底。
- `NN` 为两位序号，同一会话内递增。
- `topic` 用 kebab-case 英文，动作导向。
- 已完成的笔记由 `rfc-ship` 迁到 `docs/archive/rfc/<同一会话目录>/`，本 skill 不移动、不改状态。

结构与既有先例一致：

```markdown
# Agent Note：<动作导向的中文标题>

Status: proposed

## 问题
## 提案
## 明确不在本次范围      ← 可选，但本仓库强烈建议写
## 为什么不保留？
## 验收标准
## 风险
```

写作要求（这些是本仓库的实际标准，不是泛泛建议）：

- **正文段落写成单个物理行**，不要为了排版硬折行。
- **证据要具体到 `file:line`**，说明「做过什么检索、命中几处、都在哪」。
- **明确区分生产消费者与非生产消费者**，两者都要列。
- **`## 明确不在本次范围`**：把看似可做但被接缝保护的相邻项写清楚，并给出**为什么它们不能一起删**的技术理由。这条能挡住未来「顺手一起删」的误改。
- **`## 为什么不保留？`** 要把最强的反方理由写出来并逐条回应，不要写成自我吹捧。
- **`## 验收标准`** 要可 grep、可执行。行为一致性用现有测试名点名。
- **`## 风险`** 必须承认真实残留风险；**如果某风险能证伪，就写明证伪依据**（先例：证明「首 tick 速率是垃圾值」不成立，因为纯函数对空历史返回零）。
- 相对链接用 `../../../src/...` 形式（`docs/rfc/<会话>/` 的深度）。

**不要写日期或提交 SHA 进笔记**：它们只存在于 git 历史，rebase 后会失真。

## 广度优先，用子代理并行

用户要求广度时，**并行开多个子代理按域调查**（本仓库有效的域划分：`update` 更新子系统 / `renderer`+`tray` / `window`+`suspend` / `collector`+`main` / 依赖+构建+测试面）。每个子代理的提示词必须自带：

- 仓库绝对路径与「只读、不改文件」的硬要求。
- **只读 code，禁止读 `docs/` 下任何内容**（含 archive；待办笔记也不要整篇读）。
- **`rg` 不可用**，改用 grep 工具（搜索无需先 read 文件）。
- 生产 / 非生产 / 模糊语料的三分法。
- `AGENTS.md` 第 1–9 条的受保护清单（直接抄进提示词，**不要让子代理去读文件**）：Win32 调用顺序、`/DELAYLOAD` 与子进程隔离、单物理网卡锁定、看门狗与 `TaskbarCreated` 重建、`WM_DPICHANGED` 重嵌、挂起/恢复定时器对称、RAII 守卫归属、会话通知先 `WTSUnRegisterSessionNotification` 再 `DestroyWindow`。
- 待办笔记的路径清单（来自第 0 步的查询结果），并要求**显式报告重叠**。
- 输出格式：标题 / 符号与 `file:line` / 生产消费者（或「无」，附检索命令）/ 非生产消费者 / 提案动作 / 最强反方 / 置信度与净删行数 / 重叠。
- **必须列出被否决的候选及理由**——否则无法判断调查是否真的做过。
- 「宁可 3 条证据硬的，不要 10 条薄的」。

**不要因为第一条好候选就停止调查**；同时也不要为了凑数把薄候选写进笔记。

## 交付时同步说明

- 新增了几篇笔记、分别覆盖什么。
- 主要调查了哪些区域。
- **刻意排除了什么**（受保护接缝、被否决的候选及理由）。
- 哪一条是你自己纠错后放弃的（若有）——本仓库重视「论点被推翻就删掉，不留半对的东西」。

## 行内 TODO

只用于**小而局部、明确有用但不是耐久设计决策**的清理：

- 带稳定标签，如 `TODO(dual-default)`、`XXX(unused-config)`。
- 写清为什么可以安全回头处理、以及什么动作能简化它。
- 不要为推测性抱怨或需要笔记级决策的行为加 TODO。

需引入新的隐式约束或非直觉命令时，才考虑更新 `AGENTS.md`——它的「更新指南」禁止加入易变数值常量，要保持高信噪比。
