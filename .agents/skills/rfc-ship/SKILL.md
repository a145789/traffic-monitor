# RFC 实施：改代码 → 一个 PR → 用户确认后收口

`rfc-audit` 产出笔记；本 skill 把笔记变成代码与 PR，并在**用户确认功能 OK 之后**才标记完成。

## 只读 code + 待办笔记

文档策略以 `AGENTS.md` 为准（**已自动注入，不要再 read 一遍**）。默认不读 `docs/` 下任何内容，含 `docs/archive/`。唯一要读的文档是**你要实施的那几篇待办笔记**——它是规范，不是背景材料，只读「提案 / 明确不在本次范围 / 验收标准」三段。

## 第 0 步：确认待办范围

```
grep -rn "^Status: *proposed" docs/rfc/
```

只认 `docs/rfc/<会话目录>/` 下的笔记文件。用户指定了 RFC 就只做那些；说「都做了」就做全部待办；**查出来 0 条就如实报告「当前没有待办」**，不要自己找活干。

**PR 怎么切由你判断**（用户明确说「合一个」就合一个）：

- **单独开 PR**：有用户可观察的行为变化、碰受保护接缝、动更新协议或持久化格式，或需要用户实际试用才能验收的——「确认功能 OK」是按 PR 逐个走的，把这类和杂项捆在一起会拖住后者。
- **可以合并**：互相独立、纯内部清理、无用户可见变化、无破坏性变更的杂项；合成一个让一次验收覆盖多篇。
- **必须拆**：几篇改同一段逻辑或方向相反，拆开并说明为什么不能合。

笔记是**规范文件**：实施中发现行号、计数、事实与代码不符，**修正笔记本身**，让代码与规范一致。

## 实施

1. 先 `git status --porcelain` 确认工作区干净；有用户未提交的改动就**停下来问**，别把别人的 WIP 提进 PR。
2. 建分支，命名对应主题（`refactor/<topic>`、`feat/<topic>`）。
3. 逐条实施「提案」，**不扩大范围**；笔记的「明确不在本次范围」是硬边界。
4. **`AGENTS.md` 第 1–9 条的受保护接缝不可碰**——以那份清单为准，本 skill 不复述摘要。
5. 改动小而可评审：格式重排、无关重命名、顺手重构都会淹没有效 diff。
6. 发现笔记方案会造成**用户可观察的回归**时，停下来报告，不要照抄执行。
7. 公开 API、中文文案、协议字符串要么不变，要么在 PR 里明确写出来。

## 门禁

改完 Rust 源码后，跑 `AGENTS.md`「格式化与静态检查校验」里那四条——**它是唯一真值**（已与 CI 对齐，含 `--locked`），本 skill 不复述。门禁失败**修代码**，不要绕；删除测试导致数量下降是预期的，但必须在 PR 里点名**哪条性质由哪条更强的用例接管**。

## 提交信息五问（必须答，形式自由）

**内容必须自足，且禁止指向文档**：不许出现「详见 `docs/rfc/...`」「见 RFC 笔记」这类把答案推给别处的话——评审只读这条信息就该看懂整次改动。

1. **改了什么**：模块 / 函数 / 常量 / 依赖；公开表面（`pub` 项、消息号、协议字符串、CLI）是否变化。
2. **为什么改**：问题是什么、凭什么说它是问题——一句可核对的证据即可，不要把整篇 RFC 抄进来。
3. **对本应用的影响**：依赖与构建产物、二进制表面、协议与消息号、定时器与线程行为、发布产物；注明**哪些实测、哪些只是读代码推断**。
4. **对用户的影响**：纯内部清理就明说「无用户可见变化」；有差异写出边界；删了测试要说明没丢覆盖。
5. **是否有破坏性变更**：**必须显式写一句**「无」或「有 + 影响面与升级路径」。本项目的破坏性变更指更新协议与 `version.txt` 格式、安装器路径 / 文件名、注册表键名、窗口类名与消息号、托盘与配置的持久化格式，以及任何需要用户手工干预才能继续使用的行为变化。**拿不准按「有」写。**

**五问是要回答的内容，不是要照抄的标题**——可以合并、可以一句话带过，但每一问都得有答案。形式只有两条：分支上的中间提交有主题 + 前因/后果即可；**落到 main 的那条与 PR 描述**必须五问齐全。纯清理的小改动可以就这么短：

```
前因：<一句>   后果：<一句>
改了什么：<…>   对本应用的影响：无（未动依赖 / 产物 / 协议 / 消息号）
对用户的影响：无用户可见变化   破坏性变更：无
验证：<跑过的命令与结果>
```

**禁止为凑格式复述**（尤其别把「无用户可见变化」写三遍）。仓库风格：中文 + conventional 前缀，正文「前因：/后果：」两段，先 `git log -6` 对齐。

## PR

多篇 RFC 合进一个 PR 时**统一叙述**，不要把 N 篇笔记的标题堆起来。描述同样按五问写（小改动同样可以压到 2–3 行），另需：实际执行的验证命令与结果；一节「**本 PR 不包含**」界定边界；**诚实交代未实测项**（没跑过就写「未实测」，别用「等价性已证明」掩盖只做过静态分析）。破坏性变更即使为「无」也要写出来。

## 用户确认后才标记完成

**硬性前置：用户明确说功能 OK。** CI 绿不算。确认后对本 PR 覆盖的每篇笔记：状态行改 `Status: implemented`（**只改这一行**）；移到 `docs/archive/rfc/<同一会话>/`；不写日期或提交 SHA；**与该 PR 一起**落地（amend 或加一笔 `docs:` 提交），不留「代码已合并、规范还在待办目录」的中间态。

## 合并

**合并与改写 main 都是不可逆操作。** 合并前先向用户确认，然后：

```
gh pr merge <n> --squash --delete-branch --body-file <PR 描述文件>
```

⚠️ `--squash` **默认不会用 PR 描述**——它拼接分支上的各条提交，那样 main 上留下的是零散过程信息。必须显式 `--body-file`（`-F/--body-file`、`-t/--subject` 已确认可用），合并后 `git log -1` 复核落在 main 的那条五问齐全、且没有指向文档的引用。随后 `git fetch` → `git merge --ff-only origin/main`。

**改写 main（`--force-with-lease` 等）默认不由 agent 执行**，需要时请用户手工完成，规程见 `RUNBOOK.md`。

## 工具报错与发版

`rg` 不在 PATH（用 grep 工具或 `Select-String`）。**其它环境坑与完整发布流程见 [RUNBOOK.md](RUNBOOK.md)**——遇到工具报错、或用户要求发版时才读它，不要凭记忆操作。发布仅当用户明确要求时做，不要在实施任务里顺手发。
