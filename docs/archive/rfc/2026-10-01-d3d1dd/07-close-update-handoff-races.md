# Agent Note：收口更新交接窗口的两处竞态

Status: rejected（复核裁决：两处竞态都需新实例在毫秒级窗口内启动，频率极低且有失败恢复兜底，不实施）

## 问题

**其一，交接侧拿不到更新互斥量时照样继续。** `src/update/mod.rs:487-490` 在等到「协调者已退出」之后申请跨进程更新互斥量（`:481-486` 的注释解释了为什么刻意放在这一刻），但获取失败只写一条日志就往下走。而这个时刻正是协调者刚释放互斥量的瞬间，任何新起的 `--check-update` 都能在这个窗口里拿到它：两个更新流程于是并发——一个是正在进行安装交接的副本，另一个是刚拿到锁的检查者。检查侧的处置是「拿到就干活」（`src/main.rs:370-383` 只在拿不到时输出 `BUSY` 并静默退出），所以它不会自己让位；下载/校验/确认框会照常走完，而它的父进程（如果还在）会被安装器终结，最坏情况是一次无人消费的整包下载加一个孤儿确认框。

**其二，副本残留清理是「读时间戳 → 删除」的两次调用。** `src/update/cache.rs:60-74` 先 `metadata` + `modified` + `elapsed` 判断年龄是否超过 `UPDATE_HELPER_STALE_SECS`（`src/config.rs:190-197`，300 秒），再 `remove_file`。两步之间没有原子性；若另一实例恰在协调者「复制 → spawn」窗口内完成判断并执行删除，会把刚落盘的副本删掉，随后的 `command.spawn()` 撞 `ERROR_FILE_NOT_FOUND`——而该错误不属于重试判据（`src/update/installer.rs:456-466` 只重试共享冲突），于是交接直接失败（有失败恢复，不损坏，但用户看到一次莫名其妙的「更新没装成」）。

## 提案

1. **交接侧给互斥量加有上界重试，且上界用尽后仍继续。** 复用既有的 `INSTALLER_LAUNCH_MAX_ATTEMPTS` / `INSTALLER_LAUNCH_RETRY_DELAY_MS`（`src/config.rs:132-133`），在 `src/update/mod.rs:487` 处重试若干次；语义上保持「不让已退出的组件没人接管」这条既有方向（获取失败最终仍继续），但把「检查者插进来」的窗口从毫秒级压到「重试期间都有人占着」——因为检查侧一旦看到占用就以 `BUSY` 静默退出（`src/main.rs:370-383`、`src/update/mod.rs:189-198`），两侧的处置方向因此一致：**检查侧让位，交接侧不放弃**。
2. **副本落盘改为「临时名 + 原子替换」。** `src/update/installer.rs:435-453` 的重试回路里，把「删残留 → 直接复制到最终名」改为「复制到同目录下的唯一临时名 → `fs::rename` 覆盖最终名」（Windows 上同卷 `rename` 覆盖是原子的），这样并发清理最多删掉一个临时文件，不会让最终名出现空缺；`remove_file` 的残留清理保留但不再是正确性依赖。
3. **把两处都写成可核对的注释**：说明「交接窗口内允许并存的唯一流程是检查侧，且它以 BUSY 让位」，以及「最终名只在原子替换的瞬间变化」。

## 明确不在本次范围

- 不改「更新互斥量刻意放在等待之后申请」这个位置（`src/update/mod.rs:481-486`）：提前到 `main()` 里申请只会拿到占用，是另一件事。
- 不改 `BUSY` 的协议语义与冷却记账（`src/update/mod.rs:200-208`、`src/update/protocol.rs:507-509`）。
- 不改 `init_cleanup_temp` 的年龄门控值（`src/config.rs:190-197`）：门控的理由（避开活跃交接）是对的，本节改的是它的原子性。
- 不改副本的加锁身份绑定：那一项在 `01-bind-update-helper-identity.md`，它会把本节第二处的窗口再收窄一截（见下）。
- 不改 `acquire_exclusive_mutex` 的判重协议（`src/util.rs:188-216`，全项目唯一的 `CreateMutexW` 调用点）。

## 为什么不保留？

1. 「互斥量只是尽力而为，拿不到就该继续，否则组件没人接管。」—— 方向对，但没有理由**一次都不重试**：重试几次的代价是毫秒级等待，收益是消掉「检查与安装并发」这一整类后果。
2. 「两次调用之间的窗口极小，不值得改。」—— 判据不是窗口大小，而是「有没有一条廉价的结构性修法」。原子替换是标准的、可测的，且同时消掉「删除→复制」之间的空缺窗口。
3. 「`01` 的加锁已经能挡住并发删除。」—— 确实能：一旦副本持有只读共享句柄，另一进程的 `remove_file` 会因拿不到删除权而失败（`let _ =` 静默忽略）。但 `01` 的加锁发生在复制**之后**，且它不覆盖「临时名」缺失导致的最终名空缺；本节与 `01` 是互补的两层，不是重复。
4. 「并发检查者的后果有限。」—— 它包含一次整包下载与一个可能出现在安装器旁边的确认框；后者与安装器抢用户注意力，且其父进程若已被终结，框会成为孤儿。成本与收益不对称。

## 验收标准

- `grep -n "acquire_update_mutex" src/update/mod.rs` 命中处带循环与尝试上限，且上界常量来自 `src/config.rs:132-133`（不新造时间常量）。
- `grep -n "fs::rename\|std::fs::rename" src/update/installer.rs` 命中 ≥1 处；新增一条确定性用例：在目标文件已被他人打开（或已存在）时执行「临时名 → 覆盖」，断言最终内容为本次副本且调用返回成功。
- `grep -n "get_update_helper_path" src/update/cache.rs src/update/installer.rs` 的注释能说明「最终名只在原子替换瞬间变化」。
- 四条门禁全绿；既有 `update::installer::tests::test_cached_reuse_*` 与 `update::protocol::tests::test_named_mutex_reports_busy_then_releases` 不回归。

## 风险

- 互斥量重试期间副本仍持有安装包只读锁并占用一次进程名额；若另一侧的检查长时间不退（例如它正在等用户点确认框），重试上界用尽后仍按现状继续，行为与今天一致——本项不承诺「必然独占」。
- 原子替换要求临时文件与最终文件同目录同卷；`fs::rename` 在目标被映像加载器占用时会失败（那正是 `01` 要处理的窗口），因此两篇必须一起实施，单独实施本节会出现新的失败形态。
- 未覆盖：本机无法构造跨进程并发清理的真实竞态，上述为机制推理加代码事实。
