# Agent Note：速度显示补 GB 档（顺带解掉被单测钉死的 4096.0 MB/s），并把"互斥量"文案改成用户能懂的话

Status: implemented

## 问题

**其一，单位阶梯止于 MB。** `src/renderer.rs:356-378` 的 `format_speed_wide` 只有三档：`bytes_per_sec < 1024` 走 `B/s`（`:358-360`），否则算出十分之一整数 `x`（`:364`），`x >= 10240` 走 `MB/s`（`:365-370`），否则 `KB/s`。没有 GB 档。除以的是 `1024*1024`（MiB），所以万兆链路满速（1.25e9 B/s）显示为 `"1192.1 MB/s"`——一个 4 位数的 MB 读数。只有一条用例把它固定下来：`src/renderer.rs:667` 的 `test_format_speed_wide_boundaries`，其中 `:706-709` 断言 `u32::MAX → "4096.0 MB/s"`（u32 上限恰好是 4 GiB/s 减 1 字节，四舍五入后正好 4096.0，是数学上精确的期望，不是溢出）。也就是说：这个值不是错的，但它是"没有 GB 档"这一设计被写进测试的产物，补档必须同时改这条用例，否则改完就红。

**其二，"创建单例互斥量失败"直接弹给用户。** `src/main.rs:206-208` 在 `CreateMutexW` 失败时 `show_error("创建单例互斥量失败")`，链路是 `src/util.rs:184-186` → `:170-182` 的 `MessageBoxW`（caption 取 `APP_TITLE`，`src/config.rs:20`，图标 `MB_ICONERROR`），紧接着 `main` 直接返回——用户看到这个框之后程序就没了，没有窗口、没有托盘、没有日志（除非事先开了 `EnableDebugLog`）。"互斥量"是用户无法据以行动的实现名词；AGENTS.md 的用户文案约定只要求"新增说明性用户文案默认使用中文"，没有约束是否说人话，所以这不算违约定，但确实是产品缺陷。

生产消费者：`src/renderer.rs` 的速度绘制路径（`src/renderer.rs:410`/`:428` 用 `ARROW_UP`/`ARROW_DOWN` 与实际数值一起绘制）、`src/main.rs:253-256`（`init_single_instance` 的 `None` 分支直接 `return`）。

非生产消费者：`src/renderer.rs:667-710` 的格式边界用例组（含 `:706-709` 那条）；`src/smoke.rs:21-24` 的人工清单（不含任何文案或单位检查）。

## 提案

1. 在 `format_speed_wide` 加 `GB/s` 档，算法与既有两档同构（把阈值 `x >= 10240` 的判断放在 MB 之前：`x >= 10240` 且超过 `1024^3` 时改用 `1024^3` 做除数），整数与四舍五入的处理方式沿用 `:364` 的 `+512` 与 `:366` 的 `+524288` 同构写法，不要引入浮点（渲染路径要稳定、可在测试里逐字节断言）。
2. 更新 `test_format_speed_wide_boundaries`（`src/renderer.rs:667`）：`u32::MAX` 的期望从 `"4096.0 MB/s"` 改为 GB 档表示（按同构算法应为 `"4.0 GB/s"`），并补两条边界——恰好 `1024^3` 的输入、以及万兆量级（1.25e9）的输入，锁住"跨档阈值"与"真实链路读数"。
3. 文案改成用户能据此行动的说法。**先确认触发条件**：`show_error` 只在 `CreateMutexW` 返回 `Err` 时才弹（`src/main.rs:204-208`），"已有实例"这一支在 `src/main.rs:197-203` 就静默 `return None` 了，**结构上到不了这个框**——所以文案不能写"程序已在运行"（那会主动误导用户去做一件没用的事）。写成创建失败语义即可，例如"无法启动程序：创建单例锁失败，请重新启动；若反复出现请重启系统"。`MB_ICONERROR` 与 `APP_TITLE` 不动。

## 明确不在本次范围

- 不动 B/s 与 KB/s 的算法、不动四舍五入的整数技巧（`src/renderer.rs:364`、`:366`）——它们与显示宽度/布局绑定（`src/config.rs:54` 的 `LAYOUT_COL_WIDTH = 76`），换算法会连带改布局。
- 不扩 `u32` 位宽：`u32::MAX` = 4 GiB/s 减 1 字节，所以 GB 档在超过 4 GiB/s 的链路上仍会回到 MB 表示。这是既有位宽边界，本笔记不处理（真要处理得改 `NET_SPEED_UP/DOWN` 的类型，那是一条独立的链路）。
- 不引入本地化框架、不改英文品牌标题 `APP_TITLE`（约定明确豁免）、不改 `src/util.rs:170-182` 的 `message_box` 封装。
- 不顺手重写 `src/main.rs:206-208` 附近 `init_single_instance` 的"重复实例静默返回 None"语义（`src/main.rs:198-203`）——那是刻意的。

## 为什么不保留？

1. **"MB 读数一样能看懂"**——4 位数没有量级信息，且和"1000 多 MB"这种日常表述冲突（用户会以为是 1250 MB/s 的千兆卡）；单位阶梯的全部意义就是给出量级，缺一档等于阶梯断在最常用的那一档。
2. **"改测试就是改需求，先不动"**——那条用例钉的是一个显示格式期望，不是产品不变量；它之所以存在，正是因为当初没有 GB 档。补档时同批更新期望与新增边界，是"测试跟着事实走"，不是放宽门禁。
3. **"文案已经说了是中文"**——中文不等于可行动。用户在启动失败时唯一需要知道的是"是不是我已经开着一个了"和"我该做什么"，当前文案两个都不给。
4. **"改文案会让 issue 里的截图对不上"**——旧截图的失效成本远小于"用户看不懂启动失败"的成本。
5. **"直接删掉那个弹框、只写日志"**——不行：`main` 此时已经无法继续（没有窗口/托盘），弹框是唯一可见通道；这条不愿意删。

## 验收标准

- `grep -n "GB/s" src/renderer.rs` 命中新增档位；`src/renderer.rs:706-709` 的期望值已同步（改后 `test_format_speed_wide_boundaries` 绿）。
- 新增两条边界用例可离线跑（纯字符串函数，无需窗口/GDI），断言的是逐字节字符串而非近似。
- `grep -n "创建单例" src/main.rs` 只剩 1 处且不再是"互斥量"字样；同一条文案在 `src/main.rs:253-256` 的 `None => return` 路径上仍能弹出（人工：占用互斥量后启动第二个实例应静默、而非弹框——重复实例走的是 `src/main.rs:197-203` 的另一个分支，不要误改）。
- `cargo test --locked`、`cargo build --release --locked`、`cargo clippy --all-targets --locked -- -D warnings` 全绿。
- 人工：竖排/横排任务栏下各看一眼新档位的显示宽度没有溢出组件（`src/config.rs:48-49` 的 `DISPLAY_WIDTH/HEIGHT` 与 `src/config.rs:54` 的列宽）。

## 风险

- 新档位会让同一数值在不同版本间显示不同（`1192.1 MB/s` → `1.2 GB/s`），老截图/issue 里的数值需要重新解读；可在 README 的显示说明里加一句。
- GB 档的门槛由 `bytes_per_sec >= 1024^3` 决定，而 MB 档的舍入会把 `1024^3 - 1` 显示成 `1024.0 MB/s`，于是边界上的跳变是 `1024.0 MB/s` ↔ `1.0 GB/s`（读数连续、量级不变，只是单位与数值同时换挡），这是所有阶梯式单位显示的固有性质，不试图消除，只用新增边界用例把它固定成已知行为。
- 文案改动的措辞若把"重复启动"和"创建失败"合并得太笼统，用户仍可能误判；验收时以"一个新用户能否据此决定下一步"为准，而不是以"是否包含关键词"为准。
