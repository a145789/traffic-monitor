# Agent Note：在 README 披露更新下载会回落到第三方镜像

Status: proposed

本 note 是 07 篇拆出来的产品口径部分。它不改任何行为，只补一句对用户的披露；改动本身只有一行 README，但**措辞需要项目所有者定稿**。

## 问题

`src/update/mod.rs:58` 定义 `PROXY_HOST = "ghproxy.cn"`，`src/update/mod.rs:266-294` 在主源（`github.com`）下载安装包失败时把请求改道到该第三方镜像（`src/update/mod.rs:275-283` 的 `proxy_path`）。元数据始终只从 `github.com` 取（`src/update/mod.rs:209` 起），所以镜像**无法**伪造配套哈希——它只中转安装包字节流，而客户端对锁定句柄重算 SHA-256（`src/update/cache.rs:25-30`、`src/update/installer.rs:139-152`）后才能安装。也就是说这不是一个完整性问题，而是一个**知情问题**：用户的下载（含其 IP 与所请求的版本路径）会经过一个第三方主机，而 `README.md` 目前 `grep -n -e ghproxy -e 代理 -e 镜像 README.md` 命中 0 处。

生产消费者：`src/update/mod.rs:275-283` 是唯一的镜像回落点；非生产消费者：`docs/` 下的记录不构成对用户的披露。

## 提案

在 `README.md` 的更新说明处补一句（措辞由所有者定稿），至少传达三点：直连 `github.com` 下载失败时会回落到第三方镜像 `ghproxy.cn`；版本元数据始终来自 `github.com`；安装包在安装前仍经 SHA-256 校验。建议同时说明该回落**不可关闭**（现状如此），以免用户以为存在开关。

## 明确不在本次范围

- **不给镜像加开关或可配置项**：那是产品决策（要定默认值、失败行为、UI 落点），不与「披露」一起做。
- **不改回落逻辑本身**（顺序、超时、错误文案）：本 note 只加一句话。
- **不改元数据来源**：元数据必须继续只来自 `github.com`，这是「镜像无法伪造哈希」的前提。
- **不做「镜像域名可配置」**：可配置等于把信任面交给用户输入，属于另一个方向的改造。
- **不在本 note 里做任何 workflow 改动**：见 07 篇。

## 为什么不保留？

1. 「README 加一句镜像披露很鸡肋」——下载经过第三方是中转用户流量的行为，未披露是信任面问题；一句话的成本换来的是「用户知道自己的下载走了哪里」。
2. 「哈希校验保证了安全，披露没必要」——校验保证的是**完整性**（下到的东西没被改），不保证**知情**（用户不知道自己请求被转给了谁）。两者不是一回事。
3. 「写出来会让人以为项目不安全」——相反：主动说明「元数据只取官方源 + 安装前强校验 + 失败时走镜像」是完整的能力说明；不写清楚才会在下游讨论里被当成隐藏行为。
4. 「等有了开关再一起写」——开关是产品决策，可能长期不做；披露不应该被它阻塞。

## 验收标准

- `grep -n -e ghproxy -e 镜像 README.md` 命中 ≥ 1 处，且该段落同时出现「元数据来自 github.com」与「SHA-256 校验」两点（人工核对，不要求固定句式）。
- 不新增/不修改任何 `src/` 代码（本 note 是纯文档改动）；若实施时发现必须动代码，说明提案需要重新评审。
- 措辞由项目所有者确认后再提交（本 note 不代拟最终文案）。

## 风险

- 披露会暴露「存在第三方中转」这一事实，属于产品沟通口径；若所有者决定不披露，本 note 应被否决而不是降级实施——但届时需要另一条记录说明「已知未披露」这一决定，避免下次审计再次提出。
- 若将来更换或新增镜像域名（`src/update/mod.rs:58`），README 这句话会与代码漂移；实施时在 `PROXY_HOST` 的定义旁加注释指向该披露，让两者在同一处被提醒（不新增独立笔记）。
