# rfc（现行提案）

本目录存放**尚未实施**的 RFC 笔记，是 AI 与开发者查找「现在打算改什么」的唯一入口。

## 与 docs/archive、docs/achive 的区别

| 路径 | 含义 | AI 可读性 |
| :--- | :--- | :--- |
| **`docs/rfc/`** | **现行提案**（待办 / 在办） | **可读、应读** |
| `docs/archive/` | 历史 backup（旧 RFC、审计、调研、unsafe policy 全文） | 默认禁读，用户给出路径时例外 |

`AGENTS.md` 的「文档阅读策略」默认禁止阅读 `docs/`，理由是其中「可能过时」。**`docs/rfc/` 是本目录规定的例外**：它是现行提案，不过时，且是实施工作的依据。

## 布局：按会话分

```
docs/rfc/
  README.md                       ← 本文件
  <yyyy-mm-dd>-<会话ID片段>/       ← 一次会话的全部产出
    01-<topic>.md
    02-<topic>.md
  archive/<yyyy-mm-dd>-<会话ID片段>/  ← 已实施，保持同一会话分组
```

- **会话目录**：日期 + 会话 ID 前 6 位（如 `2026-09-10-a1b2c3`）。一个会话目录可含多篇互不相关的笔记。
- **文件名**：`NN-<topic>.md`，`NN` 为两位序号，`topic` 用 kebab-case 英文、动作导向。
- **已实施**的笔记移入 `archive/<同一会话目录>/`，**保持会话分组不变**。因此 `docs/rfc/<会话>/` 天然只含未完成项。

## 状态语义

状态行是「是否完成」的唯一真值：

```markdown
Status: proposed      ← 未实施，待办清单
Status: implemented   ← 已实施，且用户已确认功能可用
```

- 查待办：`grep -rn "^Status: *proposed" docs/rfc/`
- **`implemented` 的写入有硬性前置条件**：必须等用户明确确认功能可用，CI 绿不算。
- 标记完成时**只改这一行**，并同时把文件移入 `archive/`。两件事一起做，不存在「代码已合并、规范仍写在待办目录」的中间态。
- **不写入日期或提交 SHA**：它们只存在于 git 历史，rebase 后会失真。

## 笔记结构

与既有先例一致（`archive/2026-09-10-migration/` 下的 5 篇可直接参考）：

```markdown
# Agent Note：<动作导向的中文标题>

Status: proposed

## 问题
## 提案
## 明确不在本次范围      ← 可选，强烈建议
## 为什么不保留？
## 验收标准
## 风险
```

写作要求：

- 正文段落写成**单个物理行**，不为排版硬折行。
- 证据具体到 `file:line`，说明做过什么检索、命中几处。
- 区分**生产消费者**与**非生产消费者**（测试 / 文档 / 注释）。
- 「明确不在本次范围」要写清相邻项为何**不能**一起删——这条专门用来挡住未来「顺手一起删」的误改。
- 「风险」必须承认真实残留风险；能证伪的风险就写明证伪依据。
- 相对链接指向仓库源码。**注意随目录深度调整**：`docs/rfc/<会话>/` 下是 `../../../src/...`，移入 `archive/<会话>/` 后变 `../../../../src/...`。
