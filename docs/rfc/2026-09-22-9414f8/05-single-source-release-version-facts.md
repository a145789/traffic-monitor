# Agent Note：收敛发布链路的版本号与产物名事实，并删除失实前提的二次构建

Status: proposed

## 问题
版本号这一个事实被存了两份、读它的解析器有四套且语义互不一致：存储点是 `Cargo.toml:3`（`version = "1.5.0"`）与 `installer.iss:3`（`AppVersion=1.5.0`）；解析器分别是 `scripts/release.ts:12` 的严格 semver 正则（配 `scripts/release.ts:38` 读 Cargo.toml 的 `^version\s*=\s*"(\d+\.\d+\.\d+)"`，拒绝 dev 后缀）、`scripts/release.ts:62` 读 iss 的 `^AppVersion=(.+)$`、`scripts/package.ts:11` 读 Cargo.toml 的宽松 `^version\s*=\s*"(.+)"`、以及 `.github/workflows/release.yml:34-35` 的 `grep+sed+cut` 两条 shell 解析。改写点同样成对：`scripts/release.ts:93-100` 发版时把两文件都改写为新版本，`scripts/package.ts:47-48` 与 `:66-72` dev 打包时改写并恢复两文件（外加 `Cargo.lock`）。产物名同病：`installer.iss:8`（`OutputBaseFilename=TrafficMonitor-Setup`，不含版本）与 `.github/workflows/release.yml:118-121` 的 rename 补偿步骤、`.github/workflows/release.yml:127` 与 `:201` 的两次拼接、`scripts/package.ts:62` 的提示串。另有一处建立在失实前提上的构建：`scripts/release.ts:106-108` 注释「Build release again to verify updated dependencies compile」，但其上一行 `scripts/release.ts:104` 的 `cargo update --workspace` 只把 workspace 自身版本同步进 Cargo.lock、不更新任何 registry 依赖，「更新后的依赖」并不存在；产物 `target/release/traffic-monitor.exe` 在发版流程中也没有下游（CI 在 `.github/workflows/release.yml:47` 全新构建并上传 `:201` 处的产物）。检索记录：内置 grep `AppVersion|OutputBaseFilename|Rename installer|TrafficMonitor-Setup|post-update|cargo update --workspace`（`scripts/*.ts`、`installer.iss`、`.github/workflows/*.yml`、`Cargo.toml`）命中 12 行，逐条见上；README 检索 `bun|release\.ts|package\.ts` 0 命中（README 非消费者）。

## 提案
三项动作按侵入度递增，可分批实施。(1) 删 `scripts/release.ts:106-108` 的 post-update verification 构建（保留 `scripts/release.ts:86-88` 的 pre-guard 构建——它验证的「发版前基线可编译」是真命题），净删 3 行，每次发版省一次全量 release 编译。(2) 产物名收敛：`installer.iss:8` 改为 `OutputBaseFilename=TrafficMonitor-Setup-{#AppVersion}`（ISPP 内联同文件已有的 `AppVersion` 定义），删 `.github/workflows/release.yml:118-121` 的 rename 步骤，`.github/workflows/release.yml:127`、`:201` 与 `scripts/package.ts:62` 的拼接/提示各同步 1 行，净删约 5 行。(3)（评审裁定撤回，两档均不实施）原提案分轻档（删 `scripts/release.ts:60-70` 的 iss 前置校验，净 -11 行）与重档（ISPP `/DAppVersion=` 注入，净 -25-30 行）。撤回理由一：`scripts/release.ts:93-100` 在 commit/tag **之前**就把两文件改写为新版本，CI 的三方校验（`.github/workflows/release.yml:26-40`）在 release.ts 流程里看到的恒是愈合后的状态，前置校验是该流程里**唯一**的漂移探测器；漂移一旦存在，本地 `bun scripts/package.ts`（不带 tag、不改写 iss）编出的安装包 `AppVersion` 就与 exe 内嵌的 `CARGO_PKG_VERSION`（`src/config.rs:10`）不符，自愈会把信号连同元数据一起抹掉。撤回理由二（重档另计）：ISPP 注入触碰 AGENTS.md 明文的「非直觉验证发布命令」面，手工 ISCC 编译必须带参，CI 三方校验降为两方。故版本号事实维持「2 存 4 解析」现状，本笔记只实施 (1)(2)。

## 明确不在本次范围
`installer.iss:55` 的 `GracefulWaitTimeoutMs=5000` 与 `src/config.rs:104` 的 `MAIN_EXIT_WAIT_TIMEOUT_MS` 双写不能顺手收敛——`src/config.rs:103` 注释已显式钉死「三处调整须同步」，跨语言（Pascal/Rust）没有共享常量机制，为它建注入管道收益不成比例，且该时长是 AGENTS.md 第 4 条退出时序语义的一部分；MSRV 三写（`Cargo.toml:5`、`.github/workflows/check.yml` 的 toolchain 与 cache-key）不删——check.yml 注释声明这是刻意对账设计，消除它要在 workflow 里解析 Cargo.toml，反而新增静默漂移面；`installer.iss` 的互斥量名、`Run` 键 `ValueName`、`--quit`/`--check-update` 字面量契约（`installer.iss:5`、`:38`、`:86`、`:123`）不删——Pascal 侧无法引用 Rust 常量，这些是跨语言契约而非可收敛的重复；Bun 工具链四件套（`package.json`、`tsconfig.json`、`bun.lock`、`@types/bun`）不删——`scripts/*.ts` 是 AGENTS.md 明文的发版/打包入口（`bun scripts/release.ts`、`bun scripts/package.ts`），工具链是编辑器对这两个脚本做类型检查的真实护栏，不是演示摆设。

## 为什么不保留？
(1) 反方：pre-guard 构建已证明基线可编译，post-update 构建兜的是「版本改写把 Cargo.toml 弄坏」。回应：`scripts/release.ts:104` 的 `cargo update --workspace` 本身就解析 manifest，弄坏即刻失败；残余风险趋近零，成本却是一次全量 release 编译加一句失实注释。(2) 反方：dev 打包产物名会从固定的 `TrafficMonitor-Setup.exe` 变成带 `-devXXXX` 后缀的长名，写死旧名的仓外脚本会断。回应：仓内检索未见其他消费者，仓外不可知——故此点写进风险而非当反方否决；若评审在意，(2) 可与 (3) 重档合并，用同一套 ISPP 注入一次改到位。(3) 最强反方：重档触碰 AGENTS.md 明文记载的「非直觉验证发布命令」面，发布链路回归一次的代价（错版本安装包流出）远大于 30 行收益；且手工双击 ISCC 编译将必须显式传参，若给 `#ifndef` 留兜底默认值，兜底值又成一份表示、回到原问题。回应：此反方足以否决「重档优先」，故提案把轻档列为默认、重档仅作可选项。轻档自身的反方是「失去发版前的历史版本漂移报警」——漂移意味着上一次发版的元数据可能已出错，正确动作本是停下修复；而轻档下漂移会被 `scripts/release.ts:93-100` 自愈（两文件同时写为新版本），报警确实消失，这是真实取舍：若评审认为报警价值高于 11 行表面积，(3) 整项可放弃，(1)(2) 独立成立。

## 验收标准
`grep -n "post-update" scripts/release.ts` 0 命中；(2) 后 `grep -n "Rename installer" .github/workflows/release.yml` 0 命中、`grep -n "OutputBaseFilename" installer.iss` 的值含 `{#AppVersion}`；（(3) 已撤回，不设验收项：`grep -n "AppVersion" scripts/release.ts` 维持现状 3 处命中）；流程行为一致性点名验证：`bun scripts/package.ts dev` 必须产出带 dev 时间戳版本号的安装包（产物名若含 dev 后缀属 (2) 的预期行为变化）、`bun scripts/release.ts <更大版本>` 必须产出「三方一致」的 commit + tag 且 `.github/workflows/release.yml:26-40` 的校验步仍在、仍拒绝不一致；`git grep -n "TrafficMonitor-Setup"` 的全部拼接点必须与 (2) 后的新命名一致。

## 风险
风险一：发布链路改动只能靠真实发版完整验证——本地 `package.ts` 覆盖不到 CI 的 tag 路径（`.github/workflows/release.yml` 的 rename 与上传步只在 tag push 后执行）；缓解是分批实施：先做 (1) 这类零行为面改动，再做 (2)，每批各发一次 dev 包/预发 tag 验证。风险二：(2) 的 dev 产物名变化可能打断仓外个人脚本（仓内无消费者，仓外不可知）。风险三（已随撤回收口）：(3) 不实施，版本号事实维持「2 存 4 解析」现状，本笔记只交付 (1)(2)。
