# Agent Note：让 `reembed_if_lost` 的周期重试日志按状态去重（debug.log 的落盘与截断两条改动经复核判为净负，附否决记录）

Status: proposed

## 问题

`debug.log` 有三个已写在注释里、但没人处理的性质，一条一条说。

**其一，每行一次 open/close。** `src/util.rs:350-355` 为每条日志格式化出整行后 `OpenOptions::new().create(true).append(true).open(path)` 写一次；句柄在函数返回时析构。仓库自己在别处为热路径做过取舍（`src/util.rs:301-303` 明确说"热路径只付一次原子读"），但落盘这一段仍是每行一次系统调用。生产消费者：`log_event!`（`src/util.rs:375-381`）的全部调用点，含 `src/main.rs` 的窗口/定时器路径、`src/collector/network.rs:153` 的投递失败、`src/update/*` 的协议与安装器路径。

**其二，"环形截断"是整读 + 截断重写，且与并发写者互斥为零。** `src/util.rs:359-367` 的 `truncate_debug_log` 先 `std::fs::read` 整文件，再 `std::fs::write` 只留尾部一半（`src/config.rs:44` 的 256 KiB 阈值在 `:336-341` 判断）。`std::fs::write` 是"以截断方式打开 + 从头写"，没有临时文件、没有 rename、没有锁。写者至少三个：UI 线程、更新工作线程（`src/update/mod.rs:147-151` 起的线程，日志点如 `src/update/mod.rs:188`）、更新子进程（`src/util.rs:279` 说明 `refresh_debug_log_flag` 在主进程与子进程入口各加载一次）。`src/util.rs:346-349` 的注释自认"跨进程仍可能整行插队"，但真实损失比"插队"更重且方向单向：截断者读到内容 A 之后、写回之前，另一端 append 了一行；截断者的写回把文件截到 A 的尾部，**那一行被吞**。反之，只做 append 的子进程无法覆盖截断者的字节，只能被吞。触发条件是 >256 KiB，竖排任务栏那种刷屏场景（见下）一天就能到。

**其三，周期重试日志没有去重。** `src/window.rs:391-396` 的 `reembed_if_lost` 每次重嵌入失败写一条 `log_event!`，由 `src/config.rs:82` 的 `TIMER_INTERVAL_FULLSCREEN = 2000` 驱动（`src/main.rs:620-631` 的 tick 调用 `src/main.rs:625`）：竖排任务栏下 43200 条/天，而 256 KiB 只装得下约 1/4 天的量，于是"截断"被高频触发——与"其二"叠加成"高频写 + 高频非原子重写"。同一仓库在同类位置已有更好的做法：`src/update/installer.rs:206-208` 的 50 ms 轮询"只记首条，避免 50ms 轮询刷屏"。

非生产消费者：`README.md` 关于日志的两条说明（默认不写日志；超过 256 KB 只留尾部一半、连续 3 次写盘失败自动停写）——它们描述的是现状而不是承诺，本条不改变这两条对外语义。另需注意 `src/util.rs:375-381` 的门控意味着"其三"默认是 **0 行/天**，只有用户主动开 `EnableDebugLog` 才成立；`src/window.rs:388` 的早退又使得"已嵌入且父窗口仍是当前任务栏"时不写日志。所以本条不是"稳定刷屏"，而是"排查问题时恰好被日志噪声淹没"。

## 提案

1. **`reembed_if_lost` 去重（唯一推荐项）**：照 `src/update/installer.rs:206-208` 的既有模式，按"上一轮的失败原因"去重——状态未变只记首条，失败原因变化时才再记一条。**不要**退化成 `diag!`：`src/window.rs:394-395` 现在是 `diag!`（debug 空展开）与 `log_event!`（release 现场）各一条，去掉后者等于把一个真实的 release 现场从现场日志里删掉，是净退步。去重本身就消掉了让截断频繁触发的刷屏（43200 条/天 → 每个状态 1 条），这就是本条的主要收益：**修掉噪声源，截断竞态在实践里就基本不再触发**。
2. **【暂缓，经复核判为净负】进程内复用句柄**：把 `append_debug_log` 的 `OpenOptions::open` 换成进程级 `OnceLock<Mutex<Option<File>>>` 能省掉每行的 open/close，但**长度检查不能同时退化为进程内计数**——同一文件还有别的写者（更新工作线程、更新子进程，见 `src/util.rs:279`），本地计数看不见它们的 append，会让"超过 256 KiB 就截断"这条对 README 的承诺失效（真实大小 = 本进程计数 + 其它写者追加量；不是无界增长，因为子进程自己也会查 metadata，但上限不再被保证）。要做就得把 `src/util.rs:336-338` 的 metadata 查询原样保留，收益随之缩水到"每行省一次 open/close"，与本条"只在排查时开日志"的定位不匹配。
3. **【暂缓，经复核判为净负】截断改成原子替换**：`ReplaceFileW` 需要给 `Cargo.toml` 新增 `Win32_Storage_FileSystem` feature（`Cargo.toml:19-43` 的 feature 列表里没有），会扩大依赖面并触碰 AGENTS.md 的 release 构建资源预算；而且它对"另一进程持有的 append 句柄"并不友好——rename 换掉的是目录项，别的进程手里那个句柄仍指向被替换掉的旧文件，其后续写入会落进一个不再被引用的文件（`FILE_SHARE_DELETE` 允许 rename，旧句柄照写不误）。`src/util.rs:346-349` 那条"轻量前提"被打破的程度比原先估计的大。若将来仍要做，退而求其次的方案是"截断前复查长度 + 失败即放弃本次截断"。

## 明确不在本次范围

- 不改日志开关的真值源（注册表 `EnableDebugLog`）与"写失败 3 次自动关开关"的策略。
- 不改 256 KiB 上限与"只保留尾部一半"的比例，也不把 `debug.log` 改成滚动多文件。
- **不引入跨进程文件锁**：它会把"更新子进程只 append"这个轻量前提变成两进程争锁，且仓库在安装包缓存上已有自己的锁语义（`src/update/cache.rs:12-13`），两处混用容易出错。孤儿行问题由"单向损失 + 原子替换"消化即可。
- 不改 `diag!` 与 `log_event!` 的分工（`src/util.rs:267-274`、`:369-374`）。

## 为什么不保留？

1. **"日志是诊断功能，丢了就丢了"**——恰恰因为它是诊断功能才不能吞行：用户开日志是为了复现"更新卡住/组件消失"，而被吞掉的往往是另一进程那条关键记录（`src/update/*` 的行正是这条链路的证据）。
2. **"每行 open/close 很便宜"**——单次不贵，但它是"高频写 + 每次都要 metadata 查长度"（`src/util.rs:336-338`）的组合，在刷屏场景下每 2 秒 3 次文件系统往返；复用句柄后"把长度检查退化为进程内计数"这条曾写在这里，已删除——它会让上限失效（见提案 2）。
3. **"截断很罕见"**——刷屏场景下不罕见（见"其三"），而且罕见不等于可接受：数据丢失的概率低不代表后果轻。
4. **"rename 会被占用挡住"**——Rust 默认共享模式含 `FILE_SHARE_DELETE`，同进程/其他进程的 append 句柄理论上允许 rename，但这一条必须实测（见风险），不能靠推断。
5. **"直接删掉 debug.log 功能"**——它是唯一能拿到现场证据的通道，且 `src/util.rs` 已为它做了开关、失败计数、自动关闭三件事，成本已沉没。

## 验收标准

- 去重用例（唯一必须项）：`reembed` 的去重逻辑纯函数化后离线可测（同名 `test_*_dedup` 语义：同一失败原因连续 N 次只产出 1 条记录，原因变化产出新记录）；`grep -n "只记首条\|上次失败" src/window.rs` 能看出该意图。
- 若将来解冻提案 2/3：`grep -n "OnceLock\|Mutex<Option<File>>" src/util.rs` 与 `grep -n "ReplaceFileW\|fs::rename" src/util.rs` 各自能定位实现，且 `grep -n "metadata" src/util.rs` 必须仍然命中长度检查（不得退化为进程内计数）。
- 新增用例：`reembed` 的去重逻辑纯函数化后离线可测（同名 `test_*_dedup` 语义：同一失败原因连续 N 次只产出 1 条记录，原因变化产出新记录）。
- 人工清单补一条：两个进程同时写日志并触发截断（开日志 + 竖排任务栏复现刷屏），事后检查 `debug.log` 无半行、且另一进程的行不是被整段吞掉。
- `cargo test --locked`、`cargo clippy --all-targets --locked -- -D warnings` 全绿；`README.md` 中"超过 256 KB 只保留尾部一半""连续 3 次写盘失败自动停写"两句无需改动即可继续成立。

## 风险

- 复用句柄后，外部工具（另一进程的 rename/删除、用户手动清理）会让句柄失效；此时写失败会计入连续失败并可能在 3 次后自动关掉日志开关——即"日志自己把自己关掉"。可接受（现状也会失败），但要在注释里写明这是有意行为。
- `ReplaceFileW` 需要目标存在；首次创建与"文件刚被删"两条路径要各有一个分支，否则会出现"截断成功但文件没了"。
- 去重引入状态：`reembed_if_lost` 的"上次失败原因"必须与 `src/window.rs:388` 的早退分支共用同一个状态，否则"嵌入成功 → 再失败"会漏记一条恢复后的新失败。
- **可证伪项**：若实测发现 rename 在并发 append 下稳定失败，则第 2 条退化为"截断前复查 + 失败即放弃"，此时"其二"只被缓解而非消除——这一点必须在笔记归档时如实标注，不能宣称已修。
