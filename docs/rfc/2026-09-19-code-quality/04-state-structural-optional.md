# Agent Note：状态组织收敛与可选健壮项及暂缓项裁决

Status: proposed

## 问题

本篇收容需逐项评审的结构收敛（E1【P2】、E3【P2】、D3【P2】、B4【P2】）与按需可选的健壮项（A4【P2】、A5【P3】、F1【P3】、G【P3】），并对 E2【P2·暂缓】、D1【P3】给出暂缓裁决：E1 是 `src/collector/cpu_mem.rs:8-11` 用 `PREV_IDLE_TIME / PREV_KERNEL_TIME / PREV_USER_TIME / CPU_INITIALIZED` 四个全局原子表达「上次 CPU 采样基线」这一个概念，它们只在 UI 线程的 `WM_TIMER` 里读写（`reset_cpu_baseline` 也来自同一消息循环），原子与内存序在此没有提供任何真实保护，而 `state.rs` 模块头声称的「Acquire/Release 跨线程握手」对这些量并不成立，注释在误导后来者；E3 是 `src/main.rs:110-267` 的 155 行九阶段编排（参数、单例、优先级、IME、类注册、消息注册、看门狗、主窗口、绑定、消息循环、清理），每个阶段的错误退出路径难以一眼比对；D3 是 `src/window.rs:54-63` 的 `#[allow(clippy::too_many_arguments)]`——allow 是对坏味道的官方承认，且错误文案作为参数传来传去（调用方既传了上下文又交出了文案控制权）尤其别扭；B4 是 `src/suspend.rs:216` 的 `check_fullscreen`，「退出全屏边沿 → 重建基线 → 同步定时器 → 强制重绘」在前台无效/桌面/自身分支（`:222-233`）与正常判定分支（`:270-285`）写了两遍；A4 是 `src/tray.rs:64-65` 的 `NIM_ADD` 与 `NIM_SETVERSION` 返回值都被 `let _ =` 丢弃、之后无条件把 `nid` 存入 `TRAY_DATA`，`NIM_ADD` 失败时图标不存在而状态机以为存在，`NIM_SETVERSION` 失败时回调仍是 v0 语义（右键发 `WM_RBUTTONUP` 而非 `WM_CONTEXTMENU`）导致菜单静默失灵且无任何日志；A5 是 `src/renderer.rs:427` 的 `update_dpi` 半失败态——位图或字体创建失败时直接 `return` 保持旧尺寸，但调用方 `WM_DPICHANGED` → `embed_in_taskbar` 已按新 DPI 改了窗口物理尺寸，结果是「窗口新尺寸 + 位图旧尺寸」的 BitBlt 部分覆盖、边缘露出色键底色；F1 是全仓数十处 `let _ =`（`SetTimer`、`InvalidateRect`、`PostMessageW`、`Shell_NotifyIconW`、`DeleteObject`…）无诊断通道，多数失败确实无害但排查现场问题时只能靠读代码猜；G1/G2/G4 是百纳秒级微项。另两项本篇只给裁决、不改代码：E2【P2·暂缓】是 `src/collector/network.rs:88-131` 的 `collect_network` 写成 `with_virtual_blacklist(|blacklist| CURRENT_DATA.with(|cell| { ... INTERFACE_HISTORY.with(|hist| ...) }) })` 三层缩进、三种借用混合，中间任何一层再加状态就要四层；D1【P3】是 `src/state.rs:15-19` 三个 `pub const SUSPEND_REASON_*: u32` 配 `suspend_system(hwnd, reason: u32)`——项目已为 `SuspendReasons` 做了位协议封装，却让入口参数停留在裸整数，传 `0b101`、传 `7`、传一个定时器 ID 都能编译。

## 提案

逐项独立提交、可单独回滚：E1 收敛为 `thread_local! { static CPU_BASELINE: Cell<Option<CpuTimes>> = const { Cell::new(None) }; }`，其中 `struct CpuTimes { idle: u64, kernel: u64, user: u64 }`（`None` 即无基线，数据结构本身就表达「基线存在与否」，替掉今天的 `CPU_INITIALIZED` 布尔），`collect_cpu` 变一次 `with` 加 `match`，`reset_cpu_baseline` 变 `set(None)`，四个全局静态与虚假的内存序声明一并消失；E3 只切两刀（`main.rs:235-253` 提 `run_message_loop()`，提取时把 `GetMessageW`/`TranslateMessage`/`DispatchMessage`/`MSG` 加进 use 顺带解决 E4 的全限定路径问题；`main.rs:124-142` 提 `init_single_instance() -> Option<MutexGuard>`），阶段顺序与错误早退路径不变、行为不变，`main()` 缩到 ~90 行；D3 收敛为 `WindowSpec { class_name, title, width, height, style, ex_style }`，错误文案由 `create_window` 按类名统一生成（`「创建{类名}窗口失败」` 之类），调用方不再传 `err`；B4 抽 `on_fullscreen_edge(hwnd, was, now)`（边沿未变直接返回；离开全屏时 `reset_network_baseline` + `reset_cpu_baseline`，末尾 `sync_monitoring_timers`，离开时再 `force_repaint`）并由两分支调用，逻辑不变、`timer_plan` 系列测试不受影响；A4 让 `create_tray_icon` 返回 `bool`、失败不写 `TRAY_DATA`（`remove_tray_icon` 对不存在的图标做 `NIM_DELETE` 无害），`NIM_SETVERSION` 失败走一次 v0 兼容重试；A5 在位图或字体创建失败时维持旧尺寸嵌入（回滚本轮窗口改动，代价是跨屏后组件物理大小暂不合身，由下个成功周期自愈），保证窗口与位图尺寸一致；F1 采用 `OutputDebugStringW` 的 `diag!` 宏（`#[cfg(debug_assertions)]` 门控，release 宏体整体被 cfg 掉零成本，需在 `Cargo.toml` 补 `Win32_System_Diagnostics_Debug` feature），埋点限托盘失败、`sync_monitoring_timers` 失败、`embed_in_taskbar` 失败等十余个关键静默点，不引入 tracing/log；G 只顺手做 G1（`Layout` 缓存为 `Renderer` 字段、`update_dpi` 时重算）、G2（箭头改 `const ARROW_UP: [u16; 2] = [0x2191, 0]`）、G4（KB 分支先算 `x`，`x >= 10240` 时落入 MB 分支，含测试更新），G3（`GetIfTable2` 每秒整表分配是 API 语义，换 `GetIfEntry2` 省不了 syscall 次数）与 G5（`opt-level = "z"`）明确保持；E2（`src/collector/network.rs:88-131` 三层 `with_` 闭包并为单一 `SamplerState`，黑名单刷新成为其方法，现有 `blacklist_needs_refresh`/`rebuild_virtual_blacklist` 纯函数与测试原样保留）暂缓，落地前置条件为 PR 内写出无嵌套借用证明（`with_virtual_blacklist` 唯一调用方为 `collect_network`、`CURRENT_DATA` 只在其闭包内访问、`INTERFACE_HISTORY` 仅在采样与测试中访问、持借用下无对同一 cell 的二次 `with`），且承认三层嵌套是 thread_local 同时借用三物的固有代价、维持现状完全可辩护；D1（`src/state.rs:15-19` 裸 `u32`）降 P3，重评触发条件为新增第 4 个暂停原因或 `SuspendReasons` API 需要对模块外暴露。性能与内存：E1 从原子量改 `Cell` 在 x86 上同价且省去不必要的同步指令，G1/G2 属百纳秒级顺手做，其余各项均不新增运行时分配。

## 明确不在本次范围

UI 采集线程化（会引入句柄校验与定时器重建的全套复杂度，现状性能绰绰有余）、`with_renderer` 改 `GWLP_USERDATA`（现有注释已论证重入退化策略，替换侵入性远大于收益）、引入 clap/thiserror/log（与零依赖定位冲突）、AGENTS.md 第 1 至 7 条钉死的 Win32 时序（本项目核心资产）、E2 在证明写出前的任何代码改动、D1 在触发条件满足前的新类型，全部不做；`suspend.rs:297` 的 `WM_SETTINGCHANGE` 低频编码维持现状。此外，以下几处现有设计属禁止倒退资产，本轮不得以「整洁」之名简化：`renderer.rs` 的事务式 GDI 构造与 `into_raw` 所有权移交不重排（任何一步失败由局部 RAII 守卫自动清理，成功后 `mem::forget` 移交，Drop 里还原 stock 对象的标准释放序；A5 只加失败回滚，不动构造序与释放序）；`rate.rs` 的 u128 中转防溢出（先乘后除，回避「先截后除」在大流量+长间隔组合下的低估，注释里写明了溢出分析）不动；测试文化（每个用例都注释「这条用例钉死什么不变量、为什么别的写法测不出来」，是钉不变量而非刷覆盖率）不动，新增用例沿用同一写法；`renderer.rs` 的热路径零分配纪律（`self.buf` 复用、`write_u32` 手写格式化、`LAST_RENDERED_VALUES` 变化门控）不动——G1 缓存 `Layout` 正是为了守住它，不是替换它。

## 为什么不保留？

最强反方是「E1 原子改 `Cell` 是为将来多线程关门」。回应：当前生产消费者全在同一 UI 线程（`TIMER_ID_CPU_MEM` tick），`Cell` 与 x86 Relaxed 同价且删掉误导性内存序注释，若将来真要把采集挪到独立线程，那时连同定时器重建一起设计，现在留原子只是虚假安全感（若刻意保留则应把该意图写成注释并统一内存序——但现在没有任何此计划，YAGNI）。次强反方是「F1 的 ODS 无人看等于白埋」。回应：白埋零成本（release 空展开），且托盘失灵、定时器未起这类现场问题今天只能靠读代码猜；`eprintln!` 方案已被证伪——`src/main.rs:1` 是 `#![windows_subsystem = "windows"]`，GUI 子系统进程没有控制台，debug 构建下遇无效 stderr 句柄会直接 panic 且输出无处可看，ODS 无句柄依赖、是唯一不污染发布行为的通道。E2 暂缓的最强反方是「三个 thread_local 借用期各自独立，合并会延长借用期」——这个前提与代码事实不符：今天借用域本就链式拉满（`src/collector/network.rs:265-267` 的 `borrow()` 横跨整个采样闭包，`CURRENT_DATA` 的可变借用又包住 `INTERFACE_HISTORY` 借用），合并不实质延长任何借用期，真正的变化只有重入 panic 面从三个分散锁域合并为一个，证明义务仍在提议方。

## 验收标准

`cargo test --locked`（含 `timer_plan` 系列、CPU 基线首轮行为、托盘与 DPI 相关用例）全绿，`cargo build --release --locked`、`cargo clippy --all-targets --locked -- -D warnings`、`cargo fmt` 全绿；`grep -n "PREV_IDLE_TIME\|PREV_KERNEL_TIME\|PREV_USER_TIME\|CPU_INITIALIZED" src/collector/cpu_mem.rs` 零命中且 `grep -n "CPU_BASELINE" src/collector/cpu_mem.rs` 命中；`grep -n "too_many_arguments" src/window.rs` 零命中；`grep -rn "SamplerState" src/collector/network.rs` 在 E2 满足前置条件前零命中（暂缓即不出现）；`grep -rn "OutputDebugStringW" src` 仅出现在 `diag!` 定义与调用点；F1 会给 `Cargo.toml` 补 `Win32_System_Diagnostics_Debug` feature，按 AGENTS.md 要求必须把 `Cargo.lock` 一并提交，否则带 `--locked` 的门禁会红。

## 风险

真实残留风险三处：一是 E1 的 `thread_local` 在测试线程与 UI 线程各一份，测试若沿用全局断言会串味，证伪为现有 CPU 相关测试必须逐个确认线程归属；二是 E3 提函数时 `MutexGuard` 生命周期（`_mutex_guard` 须活到消息循环结束）被缩短，证伪为 guard 由 `init_single_instance` 返回并在 `main` 栈帧持有，diff 必须可见该绑定；三是 F1 的 `OutputDebugStringW` 宽字符串尾 NUL 与 feature 缺失导致编译失败，证伪即编译器本身，不猜测，一次过门禁为准。
